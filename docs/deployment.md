# Подготовка сервера

`compose.yaml` рассчитан на локальную разработку: сервисы опубликованы на loopback, Keycloak запускается с `start-dev`, почта уходит в Mailpit, локальная база Keycloak использует пользователя приложения. Эту конфигурацию нужно подготовить к внешнему доступу.

## Перед развёртыванием

1. Создайте отдельные домены приложения и авторизации, например `app.example.com` и `auth.example.com`, настройте HTTPS.
2. Создайте серверные секреты отдельно от локальных `.env` и `.local`. Не переносите с компьютера пароли демопользователей.
3. Выделите Keycloak отдельную базу и пользователя. Переведите его на `start`, задайте `KC_HOSTNAME=https://auth.example.com` и настройки доверенного reverse proxy.
4. В realm включите требование HTTPS. Удалите демопользователей и клиент `hackathon-cli`. Отключите регистрацию, если она не нужна; иначе настройте реальный SMTP и подтверждение почты.
5. В клиенте `hackathon-web` оставьте точные redirect URI и адрес выхода для внешнего домена. Не используйте маски на чужие адреса. Сохраните PKCE S256 и mapper audience `hackathon-api`.
6. Укажите API `APP_ENV=production`, `OIDC_ISSUER=https://auth.example.com/realms/hackathon`, внутренний адрес discovery при необходимости.
7. Для Next.js задайте `APP_ORIGIN=https://app.example.com`, тот же публичный issuer, `API_PROXY_TARGET=http://api:8080`, `SESSION_COOKIE_SECURE=true`.
8. Оставьте снаружи только reverse proxy. PostgreSQL, Redis, S3, Go API и административные интерфейсы не должны быть доступны из интернета без необходимости.
9. Настройте резервные копии базы и объектов S3, контроль свободного места и сбор логов. Проверьте восстановление до показа проекта.

`deploy/Caddyfile.example` показывает маршрутизацию доменов к контейнерам. Это заготовка для собственной серверной конфигурации; готового production Compose и автоматического деплоя здесь нет.

## Сборка и миграции

Собирайте `apps/api/Dockerfile` в контексте `apps/api`, `apps/web/Dockerfile` — в корне монорепы. Образы приложений запускаются от отдельного пользователя. Настройки upstream у Next.js читаются во время работы, поэтому домен не нужно вшивать в сборку.

Перед запуском новой версии API выполните бинарник `migrate up` из того же образа с серверным `DATABASE_URL`. Ошибка миграции должна остановить развёртывание. Используйте совместимые изменения схемы, если старая и новая версии какое-то время будут работать вместе.

## Сессии и нагрузка

Для одного экземпляра Next.js текущей схемы cookies достаточно для старта. В локальном realm ротация refresh token выключена. Если политика проекта требует ротации, нескольких экземпляров фронтенда или немедленного отзыва сессий, добавьте серверное хранилище сессий и блокировку обновления токена в Redis.

Лимит 60 изменяющих запросов в минуту на пользователя — стартовое значение. Подстройте его под действия вашего продукта. Отдельно настройте ограничения reverse proxy на вход, callback и размер запросов. Антивирус и квоты хранения в шаблоне не реализованы.

## Резервная копия

```sh
make backup
```

Команда сохраняет PostgreSQL custom dump в `.local/backups/`. Он включает базу приложения, но не базу Keycloak и не S3-объекты. Для полного восстановления нужны все три источника данных и серверная конфигурация.

Пример восстановления базы приложения в пустое локальное окружение:

```sh
docker compose exec -T postgres sh -c 'exec pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner' < .local/backups/имя-файла.dump
```

Перед восстановлением остановите приложения. Не применяйте этот пример к рабочей базе без отдельного плана: имена уже существующих таблиц вызовут конфликт.
