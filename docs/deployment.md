# Деплой на VPS

Серверный стек описан в `compose.yaml` и `compose.prod.yaml`: все Go-сервисы, две SPA, шесть PostgreSQL, Redis, RabbitMQ, S3, Keycloak, Mailpit и Ollama с Qwen. Caddy публикует только порты 80/443, получает HTTPS-сертификаты и проксирует приложение, Keycloak и тестовую почту. Остальные сервисы доступны внутри сети Compose. Реальный деплой требует подготовленного VPS; наличие workflow само по себе не подтверждает работу стенда.

Клиентская SPA обслуживается `web-service` по `/`, отдельный каркас админки — `admin-service` по `/admin/`. У приложений разные Dockerfile, сборки и образы; `web-service` передаёт `/admin/*` во внутренний Nginx админки с сохранением пути. `/admin` перенаправляется на `/admin/` с сохранением параметров запроса. API и вход обоих приложений используют общие `/api/*` и `/auth/*` через `web-service` и gateway; отдельный публичный порт для админки не нужен. Новая админка пока проверяет сессию и роль и ссылается на действующие инструменты `/dashboard/admin` в клиенте; перенос бизнес-экранов — отдельный этап. Доступ к данным по-прежнему проверяют Go-сервисы и gateway.

## Подготовка сервера

Нужен Linux VPS с Bash, Docker Engine и Docker Compose **не ниже 2.24.4**: наложение использует `!override`. Установите также `curl`, `flock` (обычно пакет `util-linux`) и `tar`. Пользователь SSH должен иметь доступ к Docker и право записи в каталог деплоя. Git, Go и Node.js на сервере не требуются: исходники приезжают архивом по SSH, сборки и подготовка настроек выполняются в контейнерах.

Ориентир для полного стека — от 8 ГБ RAM; большие модели Qwen требуют больше памяти. Оставьте место для Docker-образов, кеша сборок, нескольких версий приложения, резервных копий и модели: первая загрузка Ollama/Qwen занимает несколько гигабайт. Для небольшого стенда разумно начать с диска от 40 ГБ и контролировать его заполнение. Серверу нужен доступ в интернет к реестрам образов, зависимостям, модели и центру выдачи сертификатов.

1. Создайте два разных домена и направьте DNS на VPS: например, `app.example.org` и `auth.example.org`. Если есть AAAA-записи, IPv6 также должен вести на этот VPS.
2. Откройте входящие TCP 80/443 и выбранный порт SSH; UDP 443 используется HTTP/3. Порты баз, брокера, S3 и Ollama наружу не открывайте.
3. Подготовьте постоянный каталог, по умолчанию `/srv/boilerplate`, принадлежащий пользователю SSH.
4. Создайте в нём `.env` из `.env.example`, задайте `APP_DOMAIN=app.example.org` и `AUTH_DOMAIN=auth.example.org` без протокола и пути. Права файла — `0600`. Выберите `COMPOSE_PROJECT_NAME` до первого запуска и затем сохраняйте его: смена имени создаёт другие тома с пустыми базами.

Если `.env` ещё нет, первый запуск создаст его из шаблона и остановится с предложением заполнить домены. Заполните файл и повторите деплой новым push в `main`. Серверные секреты создаются отдельно от локальных: не переносите `.env` разработчика и `.local` на VPS.

`deploy/deploy.sh` запускает `scripts/setup.mjs --production` в контейнере Node.js. Скрипт проверяет домены, задаёт HTTPS `APP_ORIGIN`, публичный `OIDC_ISSUER`, production-режим и защищённые cookie; генерирует отсутствующие пароли и `METRICS_TOKEN`, сохраняя существующие секреты. Поля `.env` записываются в формате `KEY=value`, без shell-команд.

## Автоматический деплой

Пошаговая инструкция «проект залит в GitHub — что дальше», с DNS, двумя способами входа по SSH и разбором ошибок: [ci-cd.md](ci-cd.md).

Единственный workflow `.github/workflows/deploy.yml` запускается при push в `main`, включая слияние PR, и вручную через **Actions → Деплой → Run workflow** (ручной запуск нужен для повторной попытки после правки `.env` на сервере; задача выполняется только для ветки `main`). PR, другие ветки и теги отдельно его не запускают. Деплои выполняются последовательно, новый push не отменяет уже начатый запуск. Дополнительная блокировка `flock` защищает сервер от одновременного обновления.

В GitHub → Settings → Secrets and variables → Actions добавьте четыре секрета:

| Секрет               | Назначение                                                                   |
| -------------------- | ---------------------------------------------------------------------------- |
| `DEPLOY_HOST`        | Доменное имя или IPv4 VPS                                                    |
| `DEPLOY_USER`        | Пользователь SSH с доступом к Docker                                         |
| `DEPLOY_SSH_KEY`     | Приватный ключ; публичная часть должна быть в `authorized_keys` на VPS       |
| `DEPLOY_PASSWORD`    | Пароль пользователя — альтернатива ключу; задаётся вместо `DEPLOY_SSH_KEY`   |
| `DEPLOY_KNOWN_HOSTS` | Проверенная запись ключа сервера; отпечаток сверяется через доверенный канал |

Способ входа ровно один: заданы оба секрета или ни одного — запуск останавливается до подключения к серверу. При входе по паролю workflow ставит `sshpass` на раннере, отключает проверку ключей (`PubkeyAuthentication no`) и разрешает один запрос пароля; на сервере нужен `PasswordAuthentication yes`, а пароль попадает в секреты GitHub и становится целью перебора по SSH — ключ надёжнее. Проверка ключа сервера (`DEPLOY_KNOWN_HOSTS`, `StrictHostKeyChecking yes`) обязательна в обоих вариантах: при входе по паролю она единственное, что отличает ваш VPS от перехватившего соединение.

Необязательные **Variables**: `DEPLOY_PORT` (по умолчанию `22`) и `DEPLOY_PATH` (по умолчанию `/srv/boilerplate`, абсолютный путь без пробелов). Для нестандартного порта запись `known_hosts` должна содержать `[хост]:порт`. Секрет `DEPLOY_SCRIPT` больше не используется: актуальный `deploy/deploy.sh` передаётся вместе с архивом нужного коммита. Доступ VPS к GitHub-репозиторию не нужен.

Проверки `make check`, `make integration`, `make smoke` и `make e2e` остаются локальными командами. Workflow не запускает тесты, линтеры и сканирование образов; проверки готовности внутри деплоя нужны для подтверждения запуска сервисов. Если в branch protection или rulesets были обязательные статусы удалённого CI, снимите эти требования вручную в настройках GitHub, иначе они продолжат блокировать merge. Изменение файлов репозитория не меняет правила GitHub.

Сценарии успешного и неуспешного деплоя и подготовку production-настроек проверяет `node --test deploy/verify-deploy.mjs`: Docker и сетевые операции в этих тестах подменены, VPS не нужен.

## Что выполняет серверный скрипт

Структура постоянного каталога:

```text
/srv/boilerplate/
  .env                  # Постоянные настройки и секреты
  .project-name         # Защита от случайной смены Compose project
  .deploy.lock          # Блокировка деплоя
  shared/keycloak/      # Подготовленный шаблон первого импорта realm
  releases/<SHA>.<id>/  # Отдельные исходники каждой попытки деплоя
  backups/<дата>-<SHA>/ # tasks.dump, files.dump, notifications.dump, audit.dump, keycloak.dump
  current -> releases/<SHA>.<id>/ # Последний успешно проверенный деплой
```

1. Получает архив конкретного SHA и распаковывает отдельный release; подключает постоянные `.env` и `shared`.
2. Готовит серверные настройки, проверяет Compose и последовательно собирает десять образов приложения, включая client и admin. Образы получают тег SHA; это снижает пиковое потребление памяти и сохраняет предыдущие версии.
3. Запускает хранилища и Ollama, ждёт готовности. Перед миграциями сохраняет `pg_dump -Fc` всех шести БД, включая Keycloak.
4. Повторно запускает миграции tasks, files, notifications, audit и events; ошибка останавливает деплой. Запускает загрузку модели и ждёт её завершения.
5. Обновляет полный стек с ожиданием готовности контейнеров. Пересоздаёт web, чтобы Nginx разрешил актуальные IP gateway и admin.
6. Проверяет gateway внутри сети, затем публичные HTTPS `/healthz`, `/readyz` приложения и OIDC discovery Keycloak. Только после успеха переключает `current`.

Обычный деплой не вызывает `down` и не удаляет тома. Данные PostgreSQL, RabbitMQ, S3, модель и сертификаты сохраняются. Долгоживущие контейнеры имеют `restart: unless-stopped`. Redis хранит временные сессии: при его пересоздании пользователям потребуется войти снова. Обновление не гарантирует отсутствие короткого перерыва обслуживания.

## Вход и почта

Keycloak работает через `start` за Caddy, с публичным HTTPS hostname и доверенными proxy-заголовками. При подготовке production realm клиент `hackathon-cli` с password grant удаляется, callback и logout URI привязываются к домену приложения. Демоаккаунты сохраняются для хакатонного показа, их случайные пароли находятся в серверном `.env`.

Production setup формирует realm без тестовых пользователей. Администраторы в Keycloak не нужны: у админки свой вход, суперадминистратора создаёт сервис `identity` из `SUPERADMIN_EMAIL` и `SUPERADMIN_PASSWORD` (пароль генерирует setup), остальных админов — он сам в админке. Уже существующие тестовые аккаунты импорт не удаляет: при переносе локального окружения их нужно удалить отдельно. Локальный setup без `--production` сохраняет тестовые учётные записи для автоматических сценариев.

**Импорт не обновляет существующий realm.** Повторный setup меняет только файл импорта. При смене доменов вручную обновите redirect URI, web origins и logout URI в Keycloak. Изменение env не меняет пароли существующих пользователей и баз. При переносе локального realm удалите `hackathon-cli` и настройте HTTPS в админке отдельно.

Регистрация требует подтверждения почты. Для стенда используется Mailpit: `https://APP_DOMAIN/mail/` защищён basic-auth (`MAILPIT_USER` и `MAILPIT_PASSWORD` из `.env`). Туда приходят письма регистрации, сброса пароля и уведомления. Эти данные можно передать жюри. Для реального продукта настройте настоящий SMTP в Keycloak и notifications, определите политику регистрации и уберите демоаккаунты; текущая конфигурация рассчитана на хакатонный стенд.

## Резервные копии и восстановление

Автодеплой сохраняет пять дампов PostgreSQL перед миграциями. Это отдельные снимки БД, а не согласованный снимок всего стека: работающие сервисы могут продолжать запись. S3, настройки `.env`, данные брокера и сертификаты в эти дампы не входят. Настройте отдельное резервирование файлов, секретов и нужных томов за пределы VPS и проверяйте восстановление. Локальный `make backup` сохраняет только четыре доменные БД в `.local/backups/`, без Keycloak и S3.

Для обслуживания из успешного release можно подготовить функцию:

```bash
cd /srv/boilerplate/current
export DEPLOY_SHARED_DIR=/srv/boilerplate/shared
export DEPLOY_REVISION="$(cat .revision)"
dc() {
  docker compose --env-file /srv/boilerplate/.env \
    -f compose.yaml -f compose.prod.yaml --profile app --profile llm "$@"
}
```

Пример восстановления **в заранее подготовленную пустую БД tasks**, после остановки сервисов, которые могут в неё писать:

```bash
dc stop gateway-service tasks-service
dc exec -T tasks-postgres sh -c \
  'exec pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --exit-on-error' \
  < /srv/boilerplate/backups/дата-SHA/tasks.dump
```

Остальные пары: `files.dump` → `files-postgres`, `notifications.dump` → `notifications-postgres`, `audit.dump` → `audit-postgres`, `keycloak.dump` → `keycloak-postgres`. Перед восстановлением остановите соответствующий сервис; для Keycloak — `keycloak`. Повторное восстановление поверх рабочей БД требует отдельного плана очистки и согласования данных. Не удаляйте тома для обычного обновления.

Автоматического rollback нет. При сбое обновление могло частично примениться, а `current` остаётся ссылкой на предыдущий успешный release и не доказывает, что все контейнеры работают на нём. Для ручного возврата доступны каталоги releases, образы с SHA и дампы. Сначала оцените совместимость предыдущего кода с новой схемой: обратная миграция или восстановление БД могут потерять новые данные, а файлы S3 нужно согласовать с метаданными. Не запускайте повторный деплой старого кода вслепую.

Скрипт не удаляет старые releases, образы и backups. Настройте срок хранения и очистку по плану администратора; сохраняйте нужные версии до окончания периода восстановления. Контролируйте место, логи и состояние контейнеров.

## Смена пароля и отзыв сессий

Для обычной регистрации identity хранит `password_changed_at`. Gateway сохраняет эту версию в серверной сессии и проверяет её вместе со статусом аккаунта. При смене пароля атомарная операция Redis закрывает остальные сессии и обновляет текущую; отмена запроса браузером не отменяет эту операцию. При недоступности Redis API возвращает 503 с явным сообщением, что пароль уже изменён. После восстановления Redis старые сессии перестанут приниматься не позднее истечения кэша статуса (30 секунд). Восстановление старого снимка Redis не восстанавливает доступ: версия пароля сверяется с PostgreSQL identity. При обновлении версии приложения старые сессии без версии пароля потребуют повторного входа.
