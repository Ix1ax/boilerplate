# Подготовка сервера

Compose предназначен для локальной разработки: loopback-порты, Keycloak `start-dev`, Mailpit и демопользователи. Для сервера подготовьте отдельную конфигурацию.

1. Настройте HTTPS приложения и Keycloak на собственных доменах.
2. Создайте серверные секреты отдельно, не переносите локальные `.env` и `.local`.
3. Выделите Keycloak отдельную базу и пользователя, переключите на `start`, задайте публичный KC_HOSTNAME и доверенный reverse proxy.
4. В realm потребуйте HTTPS, удалите демопользователей и `hackathon-cli`. Настройте SMTP, подтверждение почты и нужную политику регистрации.
5. В `hackathon-web` задайте точный redirect URI `https://ваш-домен/auth/callback` и URI выхода, сохраните PKCE S256 и audience `hackathon-api`.
6. Для Go задайте `APP_ENV=production`, `APP_ORIGIN=https://ваш-домен`, `SESSION_COOKIE_SECURE=true`, публичный OIDC_ISSUER, OIDC_WEB_CLIENT_ID и внутренний OIDC_INTERNAL_URL при необходимости.
7. Nginx должен проксировать `/auth/` и `/api/` в gateway (сервис `api`; `tasks` и `files` наружу не публикуются) и раздавать SPA. API_URL `/api/v1` позволяет менять домен без пересборки. Другие VITE-переменные задаются во время сборки.
8. Публикуйте только reverse proxy; закройте PostgreSQL, Redis, S3 и административные интерфейсы.
9. Настройте резервные копии PostgreSQL, базы Keycloak и S3, сбор логов и мониторинг места. Проверьте восстановление.

`deploy/Caddyfile.example` — пример маршрутизации к web:8080 и keycloak:8080, требует общей сети. Готового production Compose здесь нет.

## Сборки и миграции

У каждого сервиса свой образ и контекст сборки: `server/gateway`, `server/tasks`, `server/files`; web собирается из корня. Все запускаются без root. Перед новой версией выполните `<сервис> migrate up` из образа этого сервиса с его `DATABASE_URL` (отдельная база на сервис). Ошибка миграции должна остановить обновление. Для production заведите отдельных пользователей Postgres на каждую базу.

## Сессии и нагрузка

Сессии хранятся в общем Redis и живут не более восьми часов. При перезапуске временного Redis потребуется повторный вход. В локальном realm ротация refresh token выключена; при включении ротации и нескольких API нужна распределённая блокировка refresh. Redis должен быть закрыт от внешнего доступа и защищён серверными секретами.

Подстройте лимит 60 изменяющих запросов в минуту на пользователя. Ограничьте частоту входов и размер запросов на reverse proxy. Квоты файлов и антивирус добавляются под требования продукта.

## Резервная копия

`make backup` сохраняет только базу приложения в `.local/backups/`. Keycloak и S3 резервируются отдельно. Пример восстановления в пустую базу после остановки приложений:

```sh
docker compose exec -T postgres sh -c 'exec pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner' < .local/backups/имя-файла.dump
```

Для рабочей базы нужен отдельный план восстановления.

## Автоматический деплой

Единственный workflow `.github/workflows/deploy.yml` запускается при push в `main`, включая слияние PR. На PR и push в другие ветки workflow не запускается. Проверки `make check`, `make integration` и `make smoke` выполняются локально. Деплои выполняются последовательно; начатый деплой не отменяется новым push.

В настройках репозитория GitHub → Secrets and variables → Actions добавьте секреты:

- `DEPLOY_HOST` — доменное имя или IPv4 сервера, SSH на порту 22.
- `DEPLOY_USER` — пользователь SSH.
- `DEPLOY_SSH_KEY` — приватный ключ этого пользователя; публичный ключ добавьте на сервер в `authorized_keys`.
- `DEPLOY_KNOWN_HOSTS` — проверенная запись ключа сервера в формате `known_hosts`. Сверьте отпечаток через доверенный канал.
- `DEPLOY_SCRIPT` — абсолютный путь к исполняемому серверному скрипту без пробелов, например `/srv/app/deploy.sh`.

Скрипт необходимо заранее создать на сервере. Он получает SHA коммита первым аргументом и должен получить исходники именно этого коммита, собрать приложение с серверной конфигурацией, выполнить миграции до обновления сервисов и проверить их готовность. При ошибке скрипт должен завершаться ненулевым кодом, чтобы workflow показал сбой. Доступ сервера к репозиторию и серверные секреты настраиваются отдельно. Без этих настроек workflow завершится ошибкой и приложение не развернётся.

## Production-наложение Compose

`compose.prod.yaml` закрывает порты хранилищ, брокера и служебных сервисов на хосте (к ним ходят только контейнеры), включает `APP_ENV=production`, защищённые cookie и обязательный `METRICS_TOKEN`:

```sh
METRICS_TOKEN=... docker compose -f compose.yaml -f compose.prod.yaml --profile app up -d --build
```

CI проверяет это наложение, собирает образы сервисов и сканирует их Trivy (CRITICAL/HIGH с доступным исправлением).
