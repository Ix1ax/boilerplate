# Бэкенд для фронтенда: что вызывать на каком экране

Шпаргалка для разработки клиента (`client/`) и админки (`admin/`). Полное описание каждой ручки, все поля и коды ответов — в Swagger: **http://localhost:3000/api/docs** (спецификации `events`, `moderation`, `notifications`, `gateway`). Модель и правила — [data-model.md](data-model.md).

Проверить, что бэкенд жив и все сценарии проходят: `make case`.

Клиентские маршруты: `/company` — заявки на поиск компании и подходящие встречи;
`/club` — подача и редактирование заявки клуба, статус допуска и причина отказа;
`/events/new` — создание встречи; `/events/:id/manage` — участники и действия
организатора; `/organizations/:id` и `/people/:id` — профиль организатора и его
ближайшие встречи. Все эти страницы требуют входа. Личный раздел — `/my`;
неиспользуемая константа `/profile` удалена. Демо-вход представителя клуба
по умолчанию открывает `/club`, сохраняя явно выбранный путь возврата.

## Как подключаться

- Все запросы — на свой origin: `/api/v1/...` и `/auth/...`. Nginx (Docker) или Vite proxy (dev) отправляют их в gateway.
- Сессия — HttpOnly cookie `starter_session`. Токенов в браузере нет, `Authorization` не нужен.
- Изменяющие запросы (POST/PUT/PATCH/DELETE) должны идти с заголовком `Origin` приложения. Браузер ставит его сам; `fetch` с `credentials: 'include'` — достаточно.
- Повторная отправка формы: заголовок `Idempotency-Key` (любой uuid) — gateway вернёт тот же ответ, а не создаст дубль.

### Вход

Два способа: **«Столото ID»** — единый вход через Keycloak (в этом контуре — тестовый стенд SSO, его страница входа оформлена как «Столото ID»), и **обычная регистрация** по почте и паролю (сервис `identity`). После любого из них браузер получает одну и ту же cookie `starter_session`, дальше разницы нет.

| Что                      | Как                                                                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Какие способы есть       | `GET /auth/providers` → `{sso: {enabled, title, login_url}, local: {enabled, register_url, login_url}}`. `local.enabled=false` — показать только «Столото ID»                                                       |
| Войти через «Столото ID» | Перейти на `/auth/login?next=/куда-вернуть` (редирект в Keycloak и обратно)                                                                                                                                         |
| Регистрация              | `POST /auth/local/register {email, password, name}` → `201 {user}`, сессия уже открыта. `409 email_taken` — «почта занята, войдите»; `422` с `field` — подсветить поле (email, password, name)                      |
| Вход по паролю           | `POST /auth/local/login {email, password}` → `200 {user}`. `401 invalid_credentials` — «неверная почта или пароль»; `403 account_blocked` — показать `error.reason`; `429` — «слишком много попыток», `Retry-After` |
| Сменить пароль           | Только при `provider: local`: `POST /auth/local/password {current_password, new_password}` → `204`. Остальные сессии пользователя закрываются                                                                       |
| Кто я                    | `GET /api/v1/me` → `{id, name, email, roles, provider}`. `provider`: `sso` или `local`. Админ — если в `roles` есть `admin` (бывает только у «Столото ID»)                                                          |
| Выйти                    | `POST /auth/logout` → `{url}`, перейти по нему (для `local` — главная приложения, для `sso` — выход из Keycloak)                                                                                                    |

Пароль: 8–128 символов, буквы и цифры, не из списка частых, не совпадает с почтой. Подтверждение почты не требуется. Учётные записи «Столото ID» для трёх ролей кейса печатает `make demo`: Анна и Игорь — пользователи; Олег — «Ладья», допущена; Мария — «Сосны», на проверке; Пётр — «Пульс», отклонена; Модератор — админ.

## Контракты

```ts
import {
  type SportEvent,
  type Organization,
  type CompanyRequest, // типы ответов
  eventInputSchema,
  eventPatchSchema,
  joinSchema,
  commentSchema, // Zod-схемы форм
  organizationInputSchema,
  companyRequestSchema,
  profilePatchSchema,
  reasonSchema,
  joinAction,
  participationLabels,
  levelLabels, // логика кнопки и подписи статусов
} from '@starter/contracts';
```

- Типы генерируются из OpenAPI (`make openapi`) — руками не правим.
- Схемы форм повторяют проверки сервера. Сервер всё равно проверяет сам и отвечает `422 {error: {code: 'validation_error', message, field}}` — подсветите поле `field`.
- Подписи статусов (`participationLabels`, `eventStatusLabels`, `organizationStatusLabels`, `quorumLabels`, `levelLabels`, `dayPartLabels`) — используйте их, чтобы одно состояние везде называлось одинаково.

## Соглашения

- **Даты** — RFC 3339 в UTC (`2026-10-24T03:00:00Z`). Показывать по Красноярску (`Asia/Krasnoyarsk`), отправлять с часовым поясом.
- **Списки** — `?limit=1..100&offset=` → `{items, total, limit, offset}`.
- **Ошибки** — `{error: {code, message, field?, request_id}}`. `message` — по-русски, можно показывать человеку как есть.

| Код | Когда                                                                | Что показать                                   |
| --- | -------------------------------------------------------------------- | ---------------------------------------------- |
| 400 | Сломанный JSON или параметры                                         | «Что-то не так с формой», это ошибка клиента   |
| 401 | Нет сессии                                                           | Отправить на вход                              |
| 403 | Нет прав: организация не допущена, чужое событие, не админ           | `message`                                      |
| 404 | Нет такого или скрыто от вас (снятое событие для постороннего)       | «Не найдено или недоступно»                    |
| 409 | Состояние не позволяет: снято, прошло, мест нет, повтор, уже решено  | `message` и перечитать данные — они изменились |
| 422 | Неверное поле или нет обязательной причины (`code: reason_required`) | Подсветить `field` / поле причины              |
| 429 | Слишком часто (60 изменений в минуту, попытки входа, жалобы)         | «Подождите», срок — в `Retry-After`            |

## Админка (`admin/`)

Все ручки — с ролью `admin` (иначе 403). Решения принимает `events`, аналитику отдаёт `moderation`.

## Что нужно знать про состояния

- **После любого действия перечитывайте затронутое:** карточку, «Мои записи», список участников. Ответ мутации уже содержит новое состояние, но рядом лежащие списки изменились тоже.
- **Снятое и отменённое событие** — для записавшихся и организатора: `status` и `moderation_reason` (плашка с причиной, кнопки записи нет). Для остальных — 404.
- **«Соберём состав»** — `min_participants`, `quorum_deadline`, `quorum_status`: `gathering` («нужно ещё N»), `reached` («встреча состоится»), `failed` (событие отменено автоматически с причиной).
- **Лист ожидания** — когда место освобождается (отмена записи, исключение, увеличение лимита), первый из листа подтверждается сам и получает уведомление.
- **Отказ и исключение окончательны:** `rejected` нельзя превратить обратно в заявку кнопкой «Записаться» — сервер отвечает 409.
- **Уведомления**, которые приходят сами: решение по заявке, исключение из состава, допуск организации, снятие или отмена события, ответ в обсуждении, скрытие и возврат сообщения, решение по жалобе, «Нашлась компания», «Состав собран», «Вас встретит…», перенос, напоминания за сутки и за 2 часа.

## Ограничения прототипа

- Посещение не проверяется: «записались», а не «пришли».
- Погода — Open-Meteo, нужен интернет у сервиса events. Без него `available: false`.
- Данные админки-аналитики отстают от действий на секунды. После очистки базы `make seed` их догоняет.
- `make case` оставляет служебные следы в демо-базе — перед показом `make reset && make demo`.

### Конкретные окна и общий вариант компании

Форма `/company` использует `companyPlanSchema` из contracts: `zones` (1–8 зон),
`windows: [{starts_at, ends_at}]` (1–20 конкретных будущих окон от часа до суток),
`expires_at` (не дальше 30 дней), спорт и уровень. Время передаётся RFC 3339 с часовым поясом.
`PATCH /my/company-requests/{id}` полностью заменяет условия своего активного запроса;
редакция увеличивается, прежние ответы на общий вариант больше не действуют.

`GET /my/company-requests/{id}/proposal` возвращает `{proposal: null}` либо общий час,
который целиком покрывается окнами реальных активных запросов с одним спортом,
общей зоной и совместимым уровнем. Версия зависит от условий и редакций участников.
Ответ: `POST /my/company-requests/{id}/proposal/response` с `{version, interested}`;
устаревшая версия — 409. Интерес не создаёт запись. `event_id` ведёт на опубликованную
подходящую встречу, `enrolled` показывает подтверждённые записи отдельно от `interested`.

`GET /sports/company-demand` доступен владельцу допущенной организации или админу:
только группы от трёх запросов, без имён и личных расписаний. Ссылка создания
предзаполняет спорт, зону, общий час и уровень; площадку и условия выбирает организатор.
Старый `/sports/demand` также скрывает счётчики групп меньше трёх.

### Настройки профиля и уведомлений

`PATCH /my/profile` принимает `about`, `city`, `level`, `interests` (до 20 названий направлений по 2–60 символов) и `preferences`. Для полной формы используется `profileSettingsSchema` из contracts. Имя меняется у поставщика учётной записи и здесь доступно только для чтения.

`preferences` содержит `large_text`, `reduced_motion`, `notify_reminders`, `notify_decisions`, `notify_replies`. Настройки возвращаются только владельцу профиля. Интересы публичны. Категории уведомлений применяются на сервере до создания события outbox, сразу ко всем каналам доставки; отсутствие значения сохраняет уведомления включёнными. Отключение доставки не скрывает статус и причину решения в кабинете или карточке встречи. Старые уведомления не удаляются.

Контакт заявки организации видят только её представитель и администратор. Публичная страница предлагает задавать вопросы в обсуждении встречи.

Заявка организации принимает также `site` (пусто или http/https URL до 500 символов), `zones` и `venues` (до 20 названий/адресов по 1–150 символов). Это свободный текст, справочник площадок не создаётся. Полная форма валидируется `organizationApplicationSchema`, подтверждение представительства остаётся полем формы и не передаётся в API. Районы, площадки и сайт доступны на публичной странице допущенного клуба; контакт заявки — только владельцу и администратору. Поля добавлены миграцией `00009_organization_locations.sql`.
