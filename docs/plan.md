# План разработки: «Платформа совместных спортивных активностей»

Рабочий план команды на финал. Требования и чек-лист баллов — в [case.md](case.md), модель данных и API — в [data-model.md](data-model.md). Здесь — **что делаем, в каком порядке и кто**.

Работаем в два трека: **бэкенд** (`server/*`, сиды, smoke, стенд) и **фронтенд** (`client/`). Точка их стыковки — OpenAPI: новую ручку сначала описываем в `server/events/api/openapi.yaml`, выполняем `make openapi`, и только потом фронтенд берёт типы из `@starter/contracts`. Так фронтенд не ждёт реализации и может работать на заглушках.

## Продуктовая идея

**«Хочу, но не с кем» → «Иду в субботу в 10:00, знаю, что взять и кого искать».**

Две опоры:

1. **«Подходит ли мне»**: карточка отвечает новичку на всё до записи — уровень, что взять, цена, «можно впервые», сколько мест и сколько новичков уже идёт. Точка сбора открывается после подтверждения.
2. **«Ищу компанию»** — наша собственная идея. Если подходящего события нет, человек оставляет запрос: «бег, новичок, утро выходных, рядом с Октябрьским». Когда кто-то создаёт подходящее событие, человек получает «Нашлась компания», а организатор ещё при создании видит «12 человек ищут такую активность». Спрос пользователей встречается с предложением организаций — это и есть целостность трёх ролей.

## Бэкенд-трек

Порядок важен: сначала то, без чего не проходят сценарии, потом собственные идеи. Каждый пункт считается готовым, когда есть OpenAPI, тест, сид (если нужен) и строка в `scripts/smoke.mjs`.

### Б0. Фундамент

- [x] Прогнать unit- и интеграционные тесты `events` и `gateway` на живом стеке.
- [x] `smoke` по 6 сценариям через API: каждый сценарий — от лица нужных демо-пользователей, с проверкой результата у другой стороны. Команда: `make case` (`scripts/case-smoke.mjs`).
- [x] `verifyEmail: false` в realm (шаблон и локальный импорт).
- [x] **«Войти как…»**: `GET /auth/demo` — список демо-аккаунтов (имя, роль, «что проверить»), `POST /auth/demo/{key}` — обычная сессия без формы Keycloak. Работает только при `DEMO_LOGIN=true`, пароли берутся из `.env`, клиенту не уходят.

### Б1. «Подходит ли мне» — доводка

- [ ] Флаг `first_time` у записи («иду впервые»): организатор видит новичков, в карточке — «из них 2 впервые».
- [ ] В выдаче и карточке: `confirmed_count`, `first_timers_count`, `spots_left`, `waitlist_position` для меня.
- [ ] Фильтр выдачи «можно впервые» (`level in (any, beginner)`).

### Б2. «Ищу компанию» — главная фича ✅

Готово: миграция `00002`, подбор при публикации в той же транзакции, уведомления через outbox, API (`/my/company-requests`, `/sports/demand`, `company_matches` у события), сиды, unit- и интеграционные тесты, сценарий в `make case`. Подробности — [data-model.md](data-model.md#company_requests-company_matches--ищу-компанию).

- Таблица `company_requests`: направление (или своё), уровень, время суток (утро/день/вечер), дни недели, район или точка с радиусом, комментарий, статус `active | closed`, срок жизни 30 дней.
- Таблица `company_matches (request_id, event_id)` — чтобы не уведомлять дважды и показывать «Подходящие события».
- При публикации события в той же транзакции находим активные запросы: направление совпадает, уровень совместим, время и день подходят, расстояние в радиусе (если есть координаты), автор не организатор. Для каждого — запись в `company_matches` и `notification.requested` в outbox.
- API: `GET/POST /my/company-requests`, `DELETE /my/company-requests/{id}`, `GET /my/company-requests/{id}/matches`, `GET /demand?sport_id=&level=` — сколько людей ищут (для формы создания события, без персональных данных).
- Сиды: 5–6 активных запросов на бег и шахматы, чтобы на демо организатор сразу видел спрос, а при создании пробежки Анне пришло «Нашлась компания».

### Б2+. Свои улучшения основного пути ✅

Готово: «Соберём состав» (минимум и срок, «Состав собран», автоотмена), «Встречу новичка» (проводники, переназначение, предупреждения организатору), напоминания за сутки и за 2 часа плюс кнопка «Напомнить», погода Open-Meteo для уличных встреч. Тесты, демо-сид, сценарий в `make case`. Подробности — [data-model.md](data-model.md).

История для защиты: **не с кем → нашлась компания → тебя встретят → напомним, что взять → игра точно состоится.**

## Фронтенд-трек

Порядок: 3 → 1 → 4 → 5 → 2 → 6 (афиша и карточка нужны всем сценариям, админка самая независимая).

| #   | Сценарий               | Экраны                                                                                                                                                 |
| --- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| —   | Вход                   | Карточки «Войти как…» (Б0) + обычная форма; переключатель роли в шапке. Навигация: Афиша · Создать · Ищу компанию · Мои записи · Организации · Админка |
| 3   | Свободная запись       | Афиша с поиском, чипами направлений и фильтрами; карточка с одной главной кнопкой, меняющей состояние                                                  |
| 1   | Создание пользователем | Форма: направление с «Добавить своё», дата, место, уровень, что взять, режим записи простыми словами, лимит; подсказка спроса из Б2                    |
| 4   | Участие по заявке      | «Подать заявку» → «Ждём решения»; управление событием: «Участники» и «Заявки», принять/отклонить с причиной                                            |
| 5   | Обсуждение             | «Вопросы и ответы» на карточке, бейдж «Организатор»                                                                                                    |
| 2   | Допуск организации     | «Моя организация»: анкета → статус → причина отказа → повторная подача; «От себя / от организации» в форме; публичная страница и каталог               |
| 6   | Снятие с публикации    | Админка: заявки организаций, мероприятия, сообщения — поиск и действия с причиной; плашка на снятом событии                                            |

Состояния кнопки записи — в одном месте: Записаться · Подать заявку · Вы участник · Заявка на рассмотрении · Отклонена (причина) · В листе ожидания (N-й) · Мест нет · Снято / отменено / прошло · Вы организатор → «Управлять». На каждом экране: скелетон, ошибка с «Повторить», пустое состояние с подсказкой, подтверждение опасных действий, вёрстка на 375px, крупный шрифт и контраст.

## Что говорим про архитектуру

Весь домен — в одном сервисе `events`: допуск организации, статус события, запись и подбор «Ищу компанию» проверяются в одной транзакции, правила доступа — в SQL. Остальные сервисы вспомогательные (уведомления, realtime, журнал) и подключены через outbox. Готовы объяснить, зачем Keycloak и RabbitMQ в прототипе, и честно назвать ограничения.
