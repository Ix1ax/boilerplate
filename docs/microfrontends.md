# Два фронтенд-приложения

Заготовка относится к критериям «Структура проекта» и «Архитектура и модель данных» в [кейсе](case.md). Приложения разделены по маршрутам: `client` обслуживает `/`, `admin` — `/admin/`. Это две самостоятельные SPA с отдельными React-root, роутерами, зависимостями, сборками и Docker-образами. Переход между ними — обычная ссылка с полной загрузкой документа.

Композиция выполняется Nginx в `web-service`, а в разработке — прокси Vite client. Runtime Module Federation не используется: приложения не встраивают компоненты друг друга. Такой способ подходит для двух самостоятельных разделов и позволяет обновлять сборки отдельно. Сценарий общего деплоя по-прежнему обновляет весь стек.

## Разработка

```sh
npm ci
npm run dev
```

Открывайте `http://localhost:3000/` и `http://localhost:3000/admin/`. Второй Vite слушает 3001, но браузер обращается к нему через 3000: gateway проверяет Origin, а OIDC callback зарегистрирован для основного адреса. Перед запуском освободите порт 3000, если его занимает Docker web-service. `make web` запускает обе SPA; `make web-client` и `make web-admin` — по отдельности. Отдельные npm-команды — `dev:client` и `dev:admin`.

Для изолированной проверки можно задать `CLIENT_DEV_PORT` и `ADMIN_DEV_PORT`; для реального входа на другом origin потребуется согласовать APP_ORIGIN и настройки Keycloak. Не меняйте их ради UI-тестов: тесты микрофронтендов подменяют только ответ `/api/v1/me`.

```sh
npm run build:client
npm run build:admin
npm run build              # обе SPA
npm run typecheck          # все workspaces
npm run lint               # обе SPA и packages
npm ci --prefix e2e        # однократно
npm run test:microfrontends --prefix e2e
```

Для браузерных тестов нужен Chromium: `cd e2e && npx playwright install chromium`. Отдельный конфиг сам поднимает Vite на 5180/5181 и проверяет гостя, роль, повтор после 503, переход в client и прямые ссылки admin. Основной `make e2e` также включает эти проверки против живого стека.

## Границы кода

- Внутри каждой SPA сохраняются слои `app → pages → widgets → features → entities → shared`.
- Импорты исходников другой SPA запрещены. Общие DTO и схемы находятся в `@starter/contracts`, независимые UI-компоненты — в `@starter/ui`.
- Admin использует существующую тему `@starter/ui`, client сохраняет текущий набор Base UI. Перенос компонентов в общий набор выполняется отдельно при необходимости.
- QueryClient и состояние React у приложений свои. Общей остаётся серверная сессия: `/api/v1/*` и `/auth/*` идут в gateway с HttpOnly cookie. Токены в JS не передаются.
- Проверка роли в admin управляет интерфейсом; доступ к административным данным продолжает проверять Go.
- PWA принадлежит client. Его service worker пропускает `/admin` и `/admin/*`, API и вход; admin не регистрирует свой worker.

## Текущая граница переноса

Новый admin — каркас с проверкой доступа и точкой входа в инструменты. Существующие статистика, журнал и отчёты пока остаются на `/dashboard/admin` в client: ссылка из нового приложения ведёт на этот экран. Их перенос в `admin/src` можно делать постепенно, вынося общие зависимости в `packages`; импортировать client напрямую нельзя.

## Docker и production

`admin/Dockerfile` собирает только admin, `client/Dockerfile` — только client. `admin-service` доступен внутри Compose и не публикует порт. `web-service` передаёт `/admin/*` в него; API и auth обрабатывает текущий gateway. Прямые ссылки admin возвращают его `index.html`, отсутствующие assets — 404. `/admin` перенаправляется на `/admin/` с сохранением query.

После добавления admin один раз пересоберите обе SPA через `make up`. При последующих изменениях можно собирать отдельно `docker compose --profile app build admin-service`. После пересоздания admin перезапустите web-service: Nginx разрешает адрес upstream при старте. Публичный адрес и OIDC-настройки остаются общими. Префикс `/admin` зарезервирован за административным приложением.
