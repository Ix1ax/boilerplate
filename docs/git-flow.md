# Git flow

Правила ветвления и релизов. Пуш в `main` запускает деплой (`.github/workflows/deploy.yml`), поэтому `main` всегда должна быть рабочей.

## Ветки

| Ветка                      | Назначение                                                                            | Откуда создаётся | Куда вливается               |
| -------------------------- | ------------------------------------------------------------------------------------- | ---------------- | ---------------------------- |
| `main`                     | Production. Каждый коммит — выпущенная версия, на него ставится тег `vX.Y.Z`.         | —                | —                            |
| `develop`                  | Интеграция готовых задач. Всегда собирается и проходит `make check`.                  | `main`           | `release/*`                  |
| `feature/<тикет>-<кратко>` | Новая функциональность, например `feature/42-llm-chat`.                               | `develop`        | `develop`                    |
| `fix/<тикет>-<кратко>`     | Исправление ошибки, найденной в `develop`.                                            | `develop`        | `develop`                    |
| `release/X.Y.Z`            | Подготовка релиза: версия, changelog, финальные правки. Новые функции не добавляются. | `develop`        | `main` и обратно в `develop` |
| `hotfix/X.Y.Z-<кратко>`    | Срочное исправление production.                                                       | `main`           | `main` и `develop`           |

Имена пишем латиницей в нижнем регистре, слова через дефис.

## Защита веток

`main` и `develop`:

- прямой пуш запрещён, изменения идут только через pull request;
- нужен хотя бы один approve и зелёный CI (`make check`);
- история линейная для `feature/*` и `fix/*` (squash merge), для `release/*` и `hotfix/*` — merge commit, чтобы сохранить границу релиза.

## Работа над задачей

```bash
git switch develop && git pull
git switch -c feature/42-llm-chat
# ... работа, небольшие коммиты ...
make check
git push -u origin feature/42-llm-chat
```

Затем откройте pull request в `develop`. Перед ревью подтяните свежий `develop` (`git rebase origin/develop` для своей ветки) и убедитесь, что `make check` проходит. Ветку удаляйте после слияния.

Правила для pull request:

- одна задача — один PR, желательно до 400 строк диффа;
- описание: что и зачем изменено, как проверить, затронуты ли контракты API, OpenAPI и миграции;
- миграции — отдельными файлами, применённые не редактируются;
- секреты и реальные адреса не коммитим, только `.env.example`.

## Коммиты

Формат [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
<тип>(<область>): <краткое описание в повелительном наклонении>
```

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `perf`. Область — модуль или сервис: `gateway`, `tasks`, `files`, `web`, `infra`, `docs`.

Примеры: `feat(files): добавить проверку квоты`, `fix(gateway): не терять Origin при проксировании`.
Ломающее изменение помечаем `!` (`feat(api)!: ...`) и описываем в теле коммита.

## Релиз

```bash
git switch develop && git pull
git switch -c release/1.4.0
# версия, changelog, финальные исправления
make check && make integration && make smoke
```

1. Pull request `release/1.4.0` → `main`, после approve — merge commit.
2. Тег на `main`: `git tag -a v1.4.0 -m "Релиз 1.4.0" && git push origin v1.4.0`. Деплой запустится от пуша в `main`.
3. Обратное слияние `main` → `develop`, чтобы правки релиза не потерялись.
4. Ветку `release/*` удалить.

Версии по [SemVer](https://semver.org/lang/ru/): `MAJOR` — несовместимые изменения API, `MINOR` — новая функциональность, `PATCH` — исправления.

## Hotfix

```bash
git switch main && git pull
git switch -c hotfix/1.4.1-session-refresh
# исправление и тест, воспроизводящий ошибку
make check
```

PR в `main` (ускоренный ревью, но approve обязателен) → тег `v1.4.1` → тот же hotfix вливается в `develop`. Если открыта `release/*`, hotfix вливается и в неё.

## Микросервисы и ветки

Репозиторий остаётся монорепой: `gateway`, `tasks`, `files` (независимые Go-модули) и `web` версионируются вместе и выпускаются одним релизом. Изменение, затрагивающее несколько сервисов (например, контракт между gateway и tasks), делается одним PR, чтобы `develop` не оказывался в состоянии, когда сервисы несовместимы. Область в сообщении коммита указывает, какой сервис изменён.

## Чего не делаем

- Не пушим в `main` и `develop` напрямую и не используем `git push --force` в общих ветках. В своей feature-ветке после rebase допустим `--force-with-lease`.
- Не коммитим `.env`, пароли и токены (в том числе `INTERNAL_TOKEN`). Утёкший секрет считаем скомпрометированным и перевыпускаем.
- Не редактируем применённые миграции и не вливаем ветки с красным CI.
