# Бэкенд админки: что есть и чего не хватает

Сверка требований кейса к администратору с кодом бэкенда. Документ отвечает на вопрос «чего не хватает админке и как это сделать на бэкенде». Каждое «есть» подтверждено ссылкой `файл:строка`. Каждое «нет» проверено поиском, команды — в разделе [Как проверено](#как-проверено). Требования взяты из [case.md](case.md) (минимум № 8–11, сценарии 2 и 6, дополнительные возможности), [data-model.md](data-model.md), [frontend-api.md](frontend-api.md) и [microfrontends.md](microfrontends.md).

## Коротко

- **Обязательный минимум кейса по админке на бэкенде закрыт.** Допуск организаций, снятие, удаление и возврат событий, скрытие сообщений, поиск организаций и событий, жалобы, справочник, учётные записи, дашборд, журнал и CSV реализованы в сервисах. Каждый маршрут закрыт ролью `admin` и в сервисе, и в gateway, описан в OpenAPI и есть в `packages/contracts`. Всего 31 маршрут, список — в [разделе 2](#2-существующие-админские-эндпоинты).
- **Фронтенд админки почти ничего из этого не вызывает.** `frontend/admin` — каркас с проверкой роли и ссылкой. `pages/dashboard-admin` в client показывает только образец `tasks` и журнал `audit` ([раздел 3](#3-что-вызывает-фронтенд-админки)). Эту часть закрывает фронтенд, бэкенд уже готов.
- **Документ разбирает все области админки** ([раздел 1а](#1а-разбор-по-областям-админки)): пользователи и роли, организации, мероприятия, записи, сообщения, жалобы, справочник, журнал и аудит, дашборд и метрики, CSV, уведомления, ИИ-подсказки. Для каждой области — что есть, чего нет и что сознательно не нужно, с причиной.
- **Недостающее на бэкенде** — 12 пунктов, подробности в [разделе 4](#4-недостающее-спецификации):
  - фильтр «события организатора-человека» для админа;
  - неполный OpenAPI у `GET /admin/events`;
  - жалобы и направления в журнале, дашборде и CSV moderation — **закрыто 2026-10-19**;
  - ИИ-помощник модерации — **частично закрыт 2026-10-19**: подсказка по жалобе;
  - модерация отзывов и историй — **частично закрыта 2026-10-19**: жалобы и решения по ним;
  - отзыв допуска организации;
  - поиск пользователей «Столото ID»;
  - тест gateway на админские префиксы;
  - уборка образца `tasks`;
  - сброс сессий пользователя админом;
  - смена представителя организации;
  - уведомление автору скрытого направления.

## 1а. Разбор по областям админки

В каждой области три вопроса: кто владеет данными, что уже есть, чего нет. Если в домене кейса что-то не нужно, это сказано прямо, с причиной. Ссылки `G…` ведут к спецификациям в [разделе 4](#4-недостающее-спецификации).

### Пользователи и роли

**Кто чем владеет.** Учётных систем три, и у каждой своя зона:

| Что                                | Владелец                                        | Где в коде                                                                                                                                                                                                        |
| ---------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Учётные записи «Столото ID»        | Keycloak                                        | Самостоятельная регистрация выключена: `infra/keycloak/realm.template.json:6`. Срок жизни access token — 300 с (`:13`). Роль `admin` из токена gateway вырезает: `server/gateway/internal/auth/auth.go:87`        |
| Администраторы админки             | identity (`admins`, `admin_history`)            | Отдельный контур: миграция `server/identity/internal/database/migrations/00002_admins.sql:4`, управление — `server/identity/internal/accounts/admin_routes.go:62` (только `superadmin`), вход для gateway — `:13` |
| Учётные записи обычной регистрации | identity                                        | Роль всегда `["user"]`: `server/identity/internal/accounts/model.go:48-50`. Статус `active`/`blocked` с причиной и история                                                                                        |
| Сессия админки                     | gateway (Redis, cookie `starter_admin_session`) | Вход, выход, смена пароля — `server/gateway/internal/auth/admin.go:132`; сверка статуса раз в 10 с (`:25`); группа `/api/v1/admin/*` только по этой сессии — `server/gateway/internal/httpapi/server.go:175`      |
| Сессии браузера                    | gateway (Redis)                                 | `server/gateway/internal/auth/session.go:178`. Индекс сессий пользователя `user_sessions:<id>` ведётся **только для обычной регистрации**: `session.go:185-195`                                                   |
| Имя, город, уровень, активность    | events (`profiles`, копия имени из gateway)     | `repository.go:1017` (`GetProfile`)                                                                                                                                                                               |

**Есть:**

- поиск обычных учётных записей по почте и имени, фильтр по статусу, карточка с историей, блокировка с причиной и разблокировка: `server/identity/internal/accounts/routes.go:80-125`;
- при блокировке вход закрывается сразу (`403 account_blocked` с причиной: `identity/.../routes.go:156`), открытые сессии — не позже чем через 30 с: gateway сверяет статус в identity (`server/gateway/internal/auth/local.go:48`, `:150-180`);
- смена пароля закрывает остальные сессии: `local.go:195-220`.

**Нет:**

- единого поиска пользователей, включая «Столото ID», и карточки с активностью → [G7](#g7);
- принудительного сброса сессий админом. У пользователей «Столото ID» сессии вообще не индексируются по пользователю, поэтому закрыть их нельзя даже кодом → [G10](#g10).

**Не нужно в продукте:**

- **Ролей у пользователей.** Админ — не роль пользователя, а отдельная учётная запись со своим входом. Управление админами есть: суперадминистратор создаёт, блокирует, удаляет их и сбрасывает пароль (`/api/v1/admin/admins`, [frontend-api.md](frontend-api.md#админка-admin)). Ни «Столото ID», ни регистрация прав модератора не дают.
- **Блокировка пользователя «Столото ID» из продукта.** Это внешний SSO компании; отключение делается в Keycloak. Продукт может только сбросить сессии ([G10](#g10)).
- **Уведомление о блокировке.** Заблокированный не может войти и видит причину на экране входа (`account_blocked` + `reason`). Колокольчик ему недоступен.

### Организации

**Есть:**

- очередь заявок и поиск: `routes.go:277`, ожидающие первыми (`repository.go:942`);
- допуск и отказ с обязательной причиной: `routes.go:306-307`, Workflow `model.go:42-45`, CHECK `00001_initial.sql:41`;
- история статусов с причинами и все события организации: `admin.go:44-58`, `:145`;
- представитель: один на организацию (`owner_id ... UNIQUE`, `00001_initial.sql:29`), админ видит его в карточке (`repository.go:849-850`);
- участники клуба: `GET /organizations/{id}/members`, админ видит любой клуб (`social_repository.go:342-347`);
- уведомление представителю о решении: `repository.go:1004-1007`;
- выгрузка `organizations.csv`: `moderation/routes.go:82`.

**Нет:**

- отзыва допуска у нарушителя → [G6](#g6);
- смены представителя (человек ушёл из клуба) → [G11](#g11).

**Не нужно:** правка карточки организации админом. По постановке организация сама правит профиль и подаёт заявку повторно, а админ только решает ([case.md](case.md#сценарий-2-допуск-организации-и-публикация-события), ветка отказа). Если админ меняет чужие данные, неясно, кто автор того, что видят пользователи.

### Мероприятия

**Есть:**

- поиск во всех статусах с фильтрами: `routes.go:308`, `parseFilter` — `routes.go:404-445`;
- карточка в любом статусе: `repository.go:156`; история публикации и состава: `admin.go:152`;
- снять, удалить, вернуть с причиной: `routes.go:338-340`; уведомления организатору и записавшимся: `repository.go:670-687`;
- после снятия записаться нельзя, API отвечает 409: проверка в SQL записи;
- выгрузка `events.csv`: `moderation/routes.go:79`.

**Нет:**

- фильтра «все события организатора-человека» → [G1](#g1);
- описания фильтров в OpenAPI → [G2](#g2).

**Не нужно:**

- **Правка события админом.** Админ не подменяет организатора: он снимает событие с причиной, организатор исправляет (`PATCH /events/{id}`), админ возвращает (`/restore`).
- **Физическое удаление.** `deleted` — мягкое удаление. Строка нужна для истории, уведомлений, плашки «Удалено» у записавшихся и журнала.

### Записи и заявки

**Есть:** админ видит всех участников и заявки с сообщениями (`repository.go:506-514`, `full := e.IsOrganizer || a.Admin`).

**Не нужно — по постановке:** решать заявки и исключать участников админ не может. «Администратор **не** рассматривает заявки участников: это делает организатор» ([case.md](case.md#обязательный-минимум), уточнения). Это проверяет SQL (`Decide`, `repository.go:536`; `RemoveParticipant`, `reports.go:371`) и живой тест `scripts/case-smoke.mjs:290-298`. Если участник нарушает правила в обсуждении, админ скрывает сообщения, а при необходимости блокирует учётную запись.

### Обсуждения и сообщения

**Есть:**

- скрыть с причиной и вернуть: `routes.go:341`, `report_routes.go:113`;
- уведомить автора, сразу обновить обсуждение у всех через realtime: `repository.go:812-821`;
- админ видит текст скрытых и удалённых сообщений: `repository.go:725`;
- лента всех сообщений с фильтрами: `moderation/routes.go:57`.

**Есть (2026-10-19):** скрыть отзыв, удалить историю и скрыть личное сообщение по жалобе — `social_moderation.go`, `HideReview` и `DeleteStory` в `social_repository.go`.

**Нет:** админских списков отзывов и историй без жалобы → [G5](#g5).

**Не нужно:**

- **Удаление сообщения админом.** Постановка требует «скрыть, обсуждение остаётся» (минимум № 10). Скрытие обратимо и сохраняет контекст для жалоб и журнала.
- **Модерация личных чатов.** Это переписка двух людей, а продукт — «не соцсеть» ([case.md](case.md#суть)). Читать её без жалобы — вторжение в приватность. ## 4. Недостающее: спецификации

Общие правила для всех пунктов (AGENTS.md):

- новый админский маршрут закрываем `platform.RequireRole("admin")` в сервисе **и** `auth.RequireRole("admin")` в gateway;
- миграции добавляем только новыми файлами;
- смена статуса пишется в одной транзакции с `status_history` через `record()`, он же ставит `domain.<сущность>.changed` в outbox (`server/events/internal/events/domain.go:49`);
- уведомление — `notify()` в той же транзакции (`repository.go:1039`);
- запись в аудит делает gateway автоматически для любого изменяющего запроса (`server.go:106-108`), отдельный код не нужен;
- после правки `server/<сервис>/api/openapi.yaml` выполняем `make openapi`, тест `api/spec_test.go` сверит маршруты.

### G1. Фильтр `organizer` в `GET /admin/events` — требование R8 (минимум № 11)

**Зачем.** Из события админ должен попасть к организатору. Если организатор — человек, нужно видеть все его события, включая снятые и отменённые. Сейчас `GET /profiles/{id}` отдаёт только опубликованные предстоящие (`repository.go:1026`), а `EventFilter.OrganizerID` (`model.go:251`) из запроса не читается.

- **Сервис:** events. **Путь:** существующий `GET /api/v1/admin/events`, новый параметр `organizer=<uuid пользователя>`.
- **Код:**
  - в `parseFilter` (`routes.go:405`) прочитать `c.Query("organizer")` и проверить `uuid.Validate`. Иначе ошибка `organizer: ожидается UUID` → 400 `invalid_query`;
  - присвоить параметр `f.OrganizerID`. SQL уже есть: `repository.go:182-184`;
  - чтобы пользовательская выдача `GET /events` не начала фильтровать по организатору, применять параметр только в админском обработчике (`routes.go:308`) или разрешить его везде: данные публичные, вреда нет.
- **Запрос:** `GET /api/v1/admin/events?organizer=6f1c…&status=published,unpublished,deleted,cancelled&limit=20`.
- **Ответ 200:**

```json
{
  "items": [
    {
      "id": "0b7e…",
      "title": "Продам абонемент в зал",
      "status": "unpublished",
      "moderation_reason": "Не спортивная активность",
      "organizer": { "id": "6f1c…", "name": "Игорь Волков" },
      "starts_at": "2026-10-24T03:00:00Z"
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

- **Ошибки:** 400 `invalid_query`, 401, 403.

### G6. Отзыв допуска организации — требование R21

**Зачем.** Допущенная организация, которая нарушает правила, сейчас остаётся `approved` навсегда: в Workflow у `approved` нет переходов (`model.go:42-45`).

- **Решение:** переход `approved → rejected` с обязательной причиной. Схема не меняется: CHECK допускает `rejected` с причиной (`00001_initial.sql:34`, `:41`). Публиковать новые события организация сразу не сможет, потому что SQL создания требует `status='approved'`. Уже опубликованные события **не трогаем**; при необходимости админ снимает их обычным `unpublish`. Это нужно явно указать в ответе и в README.
- **Код:**
  - `orgWorkflow`: `"approved": {"rejected"}`;
  - маршрут `POST /admin/organizations/{id}/revoke {reason}` в `routes.go` рядом с `:306` → `ReviewOrganization(..., "rejected", reason)`;
  - текст уведомления различать по `from`: «Допуск организации отозван: <причина>».
- **Ответ:** `Organization`. **Ошибки:** 400, 404, 409 (не `approved`), 422 `reason_required`.
- **Gateway:** без изменений (`/admin/organizations/*path`). **OpenAPI:** новый путь, `make openapi`.
- **Тесты:**
  - юнит на Workflow;
  - интеграционный: после отзыва `POST /events {as_organization:true}` → 403, событие в журнале moderation с `from=approved`.

### G7. Поиск пользователей платформы — требование R22

**Проблема.** `/admin/accounts` (identity) знает только обычную регистрацию. Пользователи «Столото ID» есть лишь в Keycloak и в копии имён `profiles` сервиса events. Из жалобы или сообщения админ не может открыть «карточку человека» с его активностью.

- **Сервис:** events (данные активности там). Маршруты в группе `/admin`:

| Метод и путь            | Параметры                                                                         | Ответ                                                                                                                        |
| ----------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `GET /admin/users`      | `q` (имя), `has_reports=true`, `sort=-reports\|-created\|name`, `limit`, `offset` | `{items: [{id, name, city, events_organized, participations, comments, comments_hidden, reports_against, created_at}], …}`   |
| `GET /admin/users/{id}` | —                                                                                 | профиль + последние 20 событий во всех статусах + последние сообщения со статусами + жалобы на него + организация, если есть |

- **SQL:** агрегаты подзапросами по `events.organizer_id`, `participations.user_id`, `comments.author_id`, `reports` (цель — его событие или сообщение). Индексы уже есть на этих колонках. Поиск — `ILIKE` с экранированием `%` и `_`, как `repository.go:946-948`.
- **Блокировка.** Для `provider=local` фронтенд ведёт на `/admin/accounts/{id}/block` (identity, тот же UUID). Для «Столото ID» блокировка — в Keycloak, вне продукта. Поле `provider` в ответе события не знают; добавлять его не нужно, фронтенд пробует `GET /admin/accounts/{id}` и показывает кнопку при 200.
- **Gateway:** префикс `/admin/users` в `server.go:155`. **OpenAPI** + `make openapi`.
- **Тесты:** интеграционный на счётчики; 403 не-админу.

### G10. Сброс сессий пользователя админом — требование R23

**Проблема.** Сессиями владеет gateway, но:

- индекс `user_sessions:<id>` пишется только для обычной регистрации (`session.go:185-195`), сессии «Столото ID» по пользователю не найти;
- ручки, чтобы админ закрыл чужие сессии, нет (поиск `admin/users/.*/sessions` пуст);
- после блокировки в identity открытые сессии живут до 30 с (`local.go:48`), а пользователь «Столото ID», отключённый в Keycloak, работает до истечения access token — до 300 с (`realm.template.json:13`).

**Решение — в gateway** (сессии больше нигде не хранятся, сервисы их не видят):

1. В `save` (`session.go:178`) добавлять id сессии в `user_sessions:<subject>` для **любой** сессии: для SSO subject берётся из проверенного ID-токена при `start`. В `/auth/logout` (`session.go:133-146`) убирать id из множества и для SSO тоже.
2. Метод `Sessions.RevokeUser(ctx, subject) (int, error)`. Lua-скрипт по образцу `revokeAfterPasswordChange` (`local.go:195-220`): удалить все `session:<id>` из множества, затем само множество и `account_active:<subject>`. Вернуть число закрытых.
3. Маршрут в `NewGateway` (`server.go`, рядом с `/admin/ping`):

```go
api.POST("/admin/users/:id/sessions/revoke", auth.RequireRole("admin"), revokeSessions(sessions[0]))
```

Владелец данных — сам gateway, поэтому проверка роли здесь единственная. Это допустимо: инвариант «роль в сервисе и в gateway» касается проксируемых маршрутов.

**Запрос:** `POST /api/v1/admin/users/6f1c…/sessions/revoke`, тело `{"reason": "Подозрение на взлом"}` (причина необязательна, попадает в аудит).

**Ответ 200:**

```json
{ "revoked": 2 }
```

**Ошибки:**

- 400 `invalid_id` — не UUID;
- 403 — не админ;
- 409 `self_revoke` — админ закрывает собственные сессии (для этого есть выход);
- 503 `session_unavailable` — Redis недоступен.

**Связка с блокировкой.** Чтобы блокировка в identity действовала сразу, а не через 30 с, фронтенд после `POST /admin/accounts/{id}/block` вызывает этот маршрут. Делать это внутри identity нельзя: identity не знает о Redis gateway, а синхронный вызов сервиса в gateway нарушает направление зависимостей. Ограничение для «Столото ID»: Keycloak SSO-cookie остаётся, и пользователь может войти снова. Полностью отключить его можно только в Keycloak — это нужно написать в подсказке рядом с кнопкой.

**Аудит:** запишется автоматически, это изменяющий запрос (`auditTrail`, `server.go:106-108`). Уведомление не нужно: пользователя просто попросят войти снова.

**OpenAPI:** путь в `server/gateway/api/openapi.yaml`, рядом с `/api/v1/admin/ping` (`:355`), затем `make openapi`.

**Тесты:**

- `session_test.go` на miniredis: SSO- и local-сессии попадают в множество, `RevokeUser` удаляет обе и возвращает 2;
- `server_test.go`: 403 для `user`, 200 для `admin`;
- `scripts/smoke.mjs`: после revoke старая cookie получает 401 на `/api/v1/me`.

### G11. Смена представителя организации — требование R24

**Проблема.** Представитель один (`owner_id ... UNIQUE`, `00001_initial.sql:29`). Если он ушёл из клуба, организация недоступна для управления, а поменять владельца нельзя: `UPDATE … SET owner_id` в коде нет (поиск `SET owner_id` пуст).

**Нужно ли.** В чек-листе кейса этого нет. Делать, только если на защите спросят «а если представитель сменился?». Иначе ответ — «новая заявка от нового представителя».

- **Сервис:** events. **Маршрут:** `POST /api/v1/admin/organizations/{id}/owner`, тело `{"user_id": "…", "reason": "Новый председатель клуба, письмо от 12.10"}`. Причина обязательна.
- **Проверки в SQL, одной транзакцией:**
  - организация есть: `FOR UPDATE`;
  - новый представитель есть в `profiles` (то есть хотя бы раз входил);
  - у него нет своей организации: UNIQUE `owner_id` даст 23505 → 409 `owner_taken`.
- **Запись:** `UPDATE organizations SET owner_id=$2, updated_at=now()`. История — `record(ctx, tx, "organization_owner", id, platform.Transition{From: старый_id, To: новый_id, Actor: actorLabel(a), Comment: reason})`. Тип `organization_owner` отобразить на сущность `organization` в `entityOf` (`domain.go:46`), как сделано для `event_quorum`: снимок уйдёт тот же, а `kind` различит смену представителя. В `Logged` (`projection.go:62-76`) для `organization` пропускать и `kind == "organization_owner"`. Условие `From == To` не сработает, потому что в `From`/`To` лежат id людей, а не статусы.
- **Уведомления:** старому — «Вы больше не представитель „…“», новому — «Вы стали представителем „…“», ссылка `/my/organization`.
- **Ответ:** `Organization` с новым `owner`. **Ошибки:** 400, 404, 409 `owner_taken`, 422 `reason_required`.
- **Gateway:** без изменений (`/admin/organizations/*path`). **OpenAPI** + `make openapi`.
- **Тест:** интеграционный — после смены старый представитель получает 403 на `POST /events {as_organization:true}`, новый — 201.

### G12. Уведомление автору скрытого направления — требование R25

**Проблема.** `SetSportHidden` (`admin.go:97-134`) пишет историю, но автору (`sports.created_by`) ничего не сообщает, хотя причина обязательна. Это единственное решение админа по контенту пользователя без уведомления.

if hidden && createdBy != "" {

Для этого `SELECT` под `FOR UPDATE` должен читать ещё `name` и `created_by`. При возврате (`show`) — «Направление „…“ снова доступно».

- **Тест:** в `admin_integration_test.go` после `hide` в outbox есть `notification.requested` для автора.
