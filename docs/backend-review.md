# Бэкенд «Вместе»: бизнес-логика и API для независимого ревью

Документ для проверяющего: что реализовано на бэкенде платформы совместных спортивных активностей (кейс Столото), по каким правилам и где это в коде. Постановка и критерии — [case.md](case.md), модель данных — [data-model.md](data-model.md), шпаргалка для фронта — [frontend-api.md](frontend-api.md). Полные контракты (поля, примеры, все коды ошибок) — `server/<сервис>/api/openapi.yaml`, общий — `packages/contracts/openapi.yaml`, Swagger — `http://localhost:3000/api/docs`.

**Просьба к ревьюеру:** искать нарушения бизнес-правил, гонки, обход прав, утечки приватных данных и расхождения кода с этим документом. В конце есть список мест, где ошибки вероятнее всего, и известные ограничения — их не нужно сообщать как новые находки.

## 1. Архитектура в двух абзацах

Браузер ходит **только в gateway** (`server/gateway`, :8080). Gateway проверяет пользователя (сессия в Redis по HttpOnly-cookie `starter_session` или Bearer JWT Keycloak), проверяет `Origin` у изменяющих cookie-запросов (CSRF), ограничивает частоту, поддерживает `Idempotency-Key` и проксирует `/api/v1/...` во внутренние сервисы. В сервисы он передаёт `X-Internal-Token` (общий секрет), `X-User-ID`, `X-User-Roles`, `X-User-Email`, `X-User-Name` (URL-кодировано). Клиентские `Authorization` и `Cookie` удаляются. Сервисы без секрета отвечают 401 и не публикуют порты.

У каждого сервиса свой Go-модуль, своя база Postgres и свои миграции (goose, только новыми файлами). Сервисы общаются только через HTTP gateway или события RabbitMQ через **transactional outbox**: событие пишется в таблицу `outbox` в той же транзакции, что и данные, relay публикует его с подтверждением брокера. Обработчики идемпотентны.

| Сервис          | Что делает                                                                                                                      |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `gateway`       | Вход двумя способами, сессии, роли, CSRF, лимиты, идемпотентность, прокси, Swagger, публикация журнала действий                 |
| `identity`      | Учётные записи обычной регистрации: хеши Argon2id, защита от подбора, блокировка админом                                        |
| `events`        | **Весь домен:** направления, организации с допуском, мероприятия, записи и заявки, обсуждение, жалобы, модерация, доп. механики |
| `moderation`    | Админка-аналитика: строит свои проекции из доменных событий `domain.*.changed`, дашборд, журнал модерации, лента сообщений, CSV |
| `notifications` | Колокольчик (REST + SSE), письма через SMTP (локально Mailpit), опционально мессенджер MAX. Слушает `notification.requested`    |
| `realtime`      | WebSocket `/api/v1/ws`, каналы `user:<id>`, `room:<имя>`, `broadcast`; сервисы пишут событием `realtime.publish`                |
| `audit`         | Журнал всех изменяющих запросов (gateway публикует `audit.recorded`)                                                            |
| `files`, `llm`  | Вложения в S3 и шлюз к локальной модели Qwen. В основной логике кейса почти не участвуют                                        |
| `tasks`         | Образец шаблона, к предметной области не относится                                                                              |

Весь домен в одном сервисе `events` — сознательно: статус организации, статус события и запись проверяются **в одной транзакции под блокировкой строки события**, без распределённой согласованности.

## 2. Пользователи, роли, вход

### 2.1. Два способа входа

| Способ                 | Как устроен                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **«Столото ID»** (SSO) | Keycloak выступает тестовым стендом корпоративного единого входа (realm оформлен как «Столото ID», самостоятельная регистрация в нём выключена). Authorization Code + PKCE S256, одноразовый `state` в Redis и cookie, обмен кода на сервере. Токены хранятся только в Redis, браузер получает id сессии. Gateway сам обновляет access token по refresh token. |
| **Почта и пароль**     | Сервис `identity`. Gateway принимает форму, вызывает внутренний API identity и создаёт такую же сессию в Redis, только вместо токенов в ней лежит проверенный пользователь (`provider: local`).                                                                                                                                                                |

Общее для обоих способов:

- Сессия живёт 8 часов с момента входа, активность её не продлевает. Cookie: HttpOnly, SameSite=Lax, Secure при HTTPS.
- При каждом входе выдаётся новый id сессии (защита от фиксации), прежняя сессия браузера удаляется.
- `POST /auth/logout` удаляет сессию в Redis. Для SSO возвращает URL выхода из Keycloak, для local — главную страницу приложения.
- Идентификатор пользователя в обоих случаях — UUID (`sub` Keycloak или `accounts.id`). Домен не различает способы входа: везде это `X-User-ID`.
- **Роли.** `user` есть у всех. `admin` выдаётся **только в Keycloak**: регистрация в identity всегда возвращает `["user"]`. Лишние поля в теле формы (например `role`) отклоняются с 400.
- **Организатор и представитель организации — не роли.** Это данные: «я организатор этого события» и «я владелец этой организации».

### 2.2. Правила обычной регистрации (identity)

- **Почта.** Обрезаются пробелы, переводится в нижний регистр, проверяется формат (`net/mail`, точка в домене, до 254 символов). Уникальность обеспечивает индекс базы, повтор — `409 email_taken`.
- **Имя.** Пробелы схлопываются, длина 2–100 символов, управляющие символы запрещены.
- **Пароль.** 8–128 символов, обязательны буквы и цифры. Запрещены пароли из списка частых и пароль, совпадающий с почтой или её частью до `@`.
- **Хранение.** Argon2id (m=19 МиБ, t=2, p=1), строка в формате PHC с солью. Не больше 4 вычислений хеша одновременно — защита памяти контейнера.
- **Вход и тайминг.** Неизвестная почта проверяется против фиктивного хеша, поэтому по времени ответа нельзя узнать, зарегистрирован ли адрес. Неизвестная почта и неверный пароль одинаково дают `401 invalid_credentials`.
- **Порядок проверок при входе:** временная блокировка → пароль → статус «заблокирован» → успех. Причину блокировки видит только тот, кто знает пароль.
- **Защита от подбора:**
  - gateway пропускает не больше 10 попыток в минуту на одну почту (ключ — хеш нормализованной почты) и не больше 600 попыток в минуту на весь сервис;
  - identity после 10 неверных паролей подряд закрывает вход на 15 минут: `429` с `Retry-After`. Счётчик атомарный в SQL, поэтому параллельные попытки порог не обходят;
  - регистраций не больше 120 в минуту на весь сервис.
- **Смена пароля** (`POST /auth/local/password`) — только для local-сессии и с текущим паролем. Новый пароль должен отличаться от текущего и пройти те же правила. После смены закрываются **все остальные** сессии пользователя (множество `user_sessions:<id>` в Redis), текущая остаётся.
- **Блокировка админом** — с обязательной причиной, история пишется в `account_history`. Вход закрывается сразу. Открытые сессии gateway закрывает при следующей сверке статуса: кеш «активен» живёт 30 секунд. Разблокировка не оживляет уже закрытые сессии.
- **Сбои.** Недоступность identity даёт `503 accounts_unavailable` и не закрывает сессии. Недоступность Redis даёт 503 и не трогает cookie.

### 2.3. API входа (gateway)

| Метод и путь                | Что                                                                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /auth/providers`       | `{sso: {enabled, title: "Столото ID", login_url}, local: {enabled, register_url, login_url}}`                                             |
| `GET /auth/login?next=`     | Редирект в Keycloak. `next` принимается только как внутренний путь: внешние, `//`, `\`, CR/LF и `/auth/*` заменяются на путь по умолчанию |
| `GET /auth/callback`        | Проверка `state`, обмен кода с PKCE, проверка токена, создание сессии. Ошибки: 400 `invalid_state`, 502 `login_failed`                    |
| `POST /auth/local/register` | `{email, password, name}` → `201 {user}` и cookie. Ошибки: 409 `email_taken`, 422 с `field`, 429, 503                                     |
| `POST /auth/local/login`    | `{email, password}` → `200 {user}` и cookie. Ошибки: 401 `invalid_credentials`, 403 `account_blocked` (с `reason`), 429                   |
| `POST /auth/local/password` | `{current_password, new_password}` → 204. Ошибки: 401 без local-сессии, 422 (`field` = `current_password` или `new_password`), 429        |
| `POST /auth/logout`         | `{url}` — куда перейти после выхода                                                                                                       |
| `GET /api/v1/me`            | `{id, email, name, roles, provider}`; гостю — 401                                                                                         |

Все изменяющие запросы с cookie требуют `Origin` = `APP_ORIGIN`, иначе 403. Внутренний API identity (`/internal/v1/accounts`, `/internal/v1/login`, `/internal/v1/accounts/{id}`, `/internal/v1/accounts/{id}/password`) доступен только с `X-Internal-Token` и наружу не проксируется.

## 3. Домен: справочник направлений

- **Справочник.** Базовые направления создаются миграцией. Пользователь при создании события передаёт **либо** `sport_id`, **либо** `sport_name` (своё направление).
- **Своё направление без правки кода:** `INSERT … ON CONFLICT (lower(btrim(name))) … RETURNING id`. «Фрисби» и « фрисби » становятся одной записью, гонка двух создателей не ломает создание. Новое направление сразу появляется в `GET /sports` и в фильтре выдачи.
- **Модерация справочника.** Админ скрывает пользовательское направление с причиной (`POST /admin/sports/{id}/hide`) или возвращает его (`/show`).
  - Базовые направления не скрываются (409).
  - На скрытом направлении нельзя создать новое событие (409), уже созданные события сохраняются.
  - `GET /admin/sports` показывает пользовательские направления первыми и где каждое используется.

## 4. Домен: организации и допуск

```
(подача) → pending → approved          админ
                   → rejected          админ, причина обязательна (CHECK в БД + workflow)
rejected → pending                     представитель исправил профиль (PUT) — повторная подача
```

- **Одна организация на представителя** (`owner_id UNIQUE`). Повторная подача — 409.
- **До одобрения:**
  - представитель видит свою заявку, её статус и причину отказа (`GET /my/organization`);
  - публичной страницы нет: для остальных `GET /organizations/{id}` отвечает 404, каталог показывает только `approved`;
  - **создать событие от имени организации нельзя: 403.** Проверка в SQL внутри транзакции создания: `organizations WHERE owner_id=$me AND status='approved'`.
- **После одобрения** события от организации публикуются **сразу**, без повторной модерации (`as_organization: true`).
- **Правка профиля.** `PUT /my/organization` у отклонённой организации переводит её в `pending` и очищает причину отказа. Правка без смены статуса тоже пишет историю и доменный снимок — так проекция админки не отстаёт.
- **Страница организации** (`GET /organizations/{id}`): данные организации, её ближайшие опубликованные события и статистика (сколько встреч проведено, сколько людей записалось).
- **Каталог** — `GET /organizations?q=`.
- **Админ:**
  - очередь заявок и поиск — `GET /admin/organizations?status=&q=`, ожидающие показываются первыми;
  - карточка — `GET /admin/organizations/{id}`: история решений с причинами и все события организации во всех статусах;
  - решение — `POST /admin/organizations/{id}/approve`, `/reject {reason}`.
  - Каждое решение пишет историю статусов, доменное событие и уведомление представителю с причиной.

## 5. Домен: мероприятия

### 5.1. Создание и поля

`POST /events`. Правила валидации:

- название 3–120 символов, описание до 5000;
- `starts_at` в будущем, `ends_at` позже начала;
- место 3–300 символов, координаты — только парой и в допустимых диапазонах;
- `level`: `any` · `beginner` · `amateur` · `pro`;
- `requirements` (что взять) до 2000, `price_note` до 200;
- `private_info` (точка сбора, контакты) до 2000;
- `join_mode`: `open` или `request`;
- `capacity` — 1–10000 или без ограничения;
- `outdoor` — уличная встреча, нужна для погоды;
- «Соберём состав» — `min_participants` 2–1000, но не больше `capacity`. `quorum_deadline` по умолчанию — за 3 часа до начала, но не раньше чем через 30 минут от текущего момента. Срок должен быть в будущем и не позже начала.

Организатор — создатель. Событие от организации хранит `organization_id`, а организатором остаётся представитель.

### 5.2. Статусы

```
(создание) → published                 сразу
published   → unpublished               админ, причина
published   → deleted                   админ, причина (мягкое удаление)
published   → cancelled                 организатор, причина (POST /events/{id}/cancel)
unpublished → published                 админ вернул (POST /admin/events/{id}/restore)
unpublished → deleted                   админ
```

Переходы проверяет `platform.Workflow`, недопустимый переход даёт 409. Каждый переход пишет историю статусов и доменное событие в той же транзакции.

**При снятии, удалении или отмене:**

- записи **сохраняются**;
- организатор (если действовал не он сам) и все `confirmed`/`pending`/`waitlist` получают уведомление с причиной;
- открытые жалобы на событие закрываются с пометкой «меры приняты».

### 5.3. Видимость и выдача

- **Карточка `GET /events/{id}`:**
  - `published` видят все вошедшие;
  - `unpublished`/`deleted`/`cancelled` видят только организатор, люди с записью на событие (с плашкой и причиной) и админ. Остальным — **404**.
- **`private_info`** приходит только организатору и подтверждённым участникам. Остальные получают `has_private_info: true/false`. Заявка `pending` точку сбора **не** открывает.
- **Выдача `GET /events`** показывает только `published` и ещё не закончившиеся события. Параметры:
  - полнотекстовый поиск `q` (русская морфология, GIN), до 100 символов;
  - `sport` — до 20 UUID через запятую;
  - `level` (`beginner` включает «для всех»), `mode` (`open`/`request`), `from`/`to`, `organization`;
  - гео: `near=lat,lng` + `radius_km` (до 100, ближайшие первыми, в ответе `distance_km`) или `bbox`. NaN и Inf отклоняются с 400;
  - пагинация `limit` 1–100, `offset` до 100000.
- **В карточке и выдаче:** `spots_left`, `first_timers_count`, `quorum_status`, `my_participation` (статус, `decision_reason`, проводник), `is_organizer`, данные организатора со ссылкой на профиль или организацию.
- **Админ:** `GET /admin/events?status=&q=…` — поиск во всех статусах; `GET /admin/events/{id}/history` — история публикации и состава.

### 5.4. Правка и перенос (`PATCH /events/{id}`)

- Править может только организатор, только опубликованное и ещё не начавшееся событие.
- После публикации **нельзя менять:** режим записи, направление и «от чьего имени».
- Правка объединяется с текущим состоянием и проходит те же правила, что и создание. Исключение: прошедший `quorum_deadline` не мешает поправить место или название, если не меняется время начала (это исправленная ошибка).
- **Под блокировкой события проверяется повторно:** правит именно организатор, событие опубликовано, новый `capacity` не меньше числа подтверждённых — иначе 422.
- **После сохранения освободившиеся места сразу получает лист ожидания** — тоже исправленная ошибка: раньше увеличение лимита отдавало места новым людям в обход очереди.
- **Уведомления записавшимся:**
  - смена времени или места — «Перенос: было → стало», напоминания сбрасываются и придут заново от нового времени;
  - смена условий (уровень, что взять, цена, точка сбора) — «Организатор обновил условия».
- Перенос начала пересчитывает срок сбора состава. Если меняется только начало, длительность события сохраняется.

## 6. Домен: запись и заявки

### 6.1. Переходы участия

```
open:     (запись) → confirmed            или waitlist, если мест нет
request:  (заявка) → pending → confirmed | rejected     решает только организатор
confirmed | pending | waitlist → cancelled                пользователь передумал (DELETE /events/{id}/join)
confirmed | waitlist → rejected                           организатор исключил с причиной (POST …/participants/{pid}/remove)
cancelled → pending | confirmed | waitlist                повторная запись обновляет ту же строку
rejected  → —                                             окончательно: повторная запись — 409
```

### 6.2. Инварианты записи (`POST /events/{id}/join`)

1. Транзакция начинается с `SELECT … FROM events WHERE id=$1 FOR UPDATE`. В том же порядке блокировок работают решение по заявке, снятие, правка, исключение, автоотмена и уход из события.
2. Событие должно быть `published` и ещё не закончиться, иначе 409. **Снятое событие не принимает запись даже по прямой ссылке или прямому POST.**
3. Организатор не может записаться на своё событие (409).
4. Уникальность `(event_id, user_id)` обеспечивает база. Повторный клик при активной записи возвращает текущее состояние без дубля и без нового уведомления.
5. Подтверждённые считаются против `capacity` под блокировкой: два одновременных запроса на последнее место не переполняют лимит, второй попадает в `waitlist`.
6. `pending` и `waitlist` **не** входят в счётчик мест и не видят `private_info`.
7. Отказ или исключение окончательны (409 «повторная запись недоступна»). Иначе решение организатора отменялось бы повторным нажатием «Записаться».
8. Организатор получает уведомление о каждой новой записи, заявке и записи в лист ожидания.

### 6.3. Решение по заявке

`POST /events/{id}/participants/{pid}/approve` · `/reject {reason?}`:

- решать может **только организатор события**. Админ не может: это не его решение (403);
- только по заявке в статусе `pending` (409 «уже рассмотрена»);
- при принятии повторно проверяется лимит мест (409 «мест нет»);
- участник получает уведомление; при принятии запускаются «Соберём состав» и подбор проводника.

### 6.4. Лист ожидания и освобождение мест

Место освобождается, когда:

- подтверждённый участник отменил запись;
- организатор исключил участника;
- организатор увеличил или снял лимит.

Тогда под той же блокировкой первые из `waitlist` (по `created_at`, затем по `id`) подтверждаются **в цикле, пока есть места**, и получают уведомление «Освободилось место». Очередь работает только у открытых событий, пока событие опубликовано и не закончилось.

### 6.5. Участники

`GET /events/{id}/participants`:

- организатор и админ видят все записи со статусами и сообщениями к заявкам (сначала `pending`, затем `confirmed`, затем `waitlist`);
- остальные видят только подтверждённых: имя, уровень, отметки «впервые» и «проводник».

**Исключение участника** (`POST …/participants/{pid}/remove {reason}`):

- только организатор, событие опубликовано и не закончилось;
- исключить можно `confirmed` или `waitlist`, причина обязательна;
- пара «новичок — проводник» распадается;
- участник получает уведомление с причиной, место переходит очереди.

### 6.6. Мои записи и события

- `GET /my/participations` — все статусы, включая снятые и отменённые события с причиной. Прошедшие идут в конце.
- `GET /my/events` — мои события как организатора во всех статусах.

## 7. Домен: обсуждение

- `GET /events/{id}/comments` — обсуждение доступно тем, кто может видеть событие. Для открытого события это **любой вошедший пользователь**, запись не нужна.
- `POST /events/{id}/comments {body, parent_id?}`:
  - длина 1–2000 символов;
  - писать можно, пока событие `published`;
  - ответ — только на сообщение **верхнего уровня этого же события**, иначе 422.
- **Авторство различимо:** `is_organizer` вычисляется при чтении (`author_id = organizer_id`). Для события организации добавляется `organization_name`.
- **Уведомления:** организатору — о новом вопросе (если писал не он), автору вопроса — об ответе. Открытые страницы получают сигнал `comments.changed` в канал `room:event:<id>`; данные клиент перечитывает из API.
- **Статусы сообщения:**

```
visible → hidden     админ, причина обязательна (POST /admin/comments/{id}/hide)
hidden  → visible    админ вернул (POST /admin/comments/{id}/restore)
visible → deleted    автор удалил своё (DELETE /events/{id}/comments/{cid}); необратимо
```

- **Текст скрытого или удалённого сообщения** не отдаётся никому, кроме админа: у остальных `body` пустой, есть `status` и `hidden_reason`. Ответы и остальное обсуждение сохраняются.
- **При скрытии** автор получает уведомление с причиной, а открытые жалобы на сообщение закрываются как «меры приняты».
- **При удалении автором** жалобы тоже закрываются. **При возврате** автор получает уведомление.

## 8. Жалобы

Жалоба — сигнал модератору. Сама по себе она данные **не** меняет.

- **Подать:**
  - на событие — `POST /events/{id}/report {reason, details?}`;
  - на сообщение — `POST /events/{id}/comments/{cid}/report`;
  - `reason`: `spam` · `offensive` · `fraud` · `wrong_info` · `dangerous` · `other`. Для `other` пояснение обязательно, пояснение до 1000 символов.
- **Проверки при подаче:**
  - событие должно быть видно жалующемуся (те же правила, что у карточки);
  - сообщение должно быть видимым и принадлежать этому событию, иначе 404;
  - на своё событие или своё сообщение жаловаться нельзя (409);
  - одна открытая жалоба человека на одну цель (частичный уникальный индекс), повтор — 409;
  - не больше 20 жалоб в час от одного человека (429).
- **Очередь админа** — `GET /admin/reports?status=&target_type=`:
  - сначала открытые жалобы, среди них — цели с наибольшим числом открытых жалоб;
  - в каждой: краткое описание цели (название события, оригинальный текст сообщения или начало описания события), автор цели, её текущий статус и автор жалобы.
- **Принять жалобу** — скрыть сообщение или снять (удалить) событие обычными маршрутами. Все открытые жалобы на цель закрываются как `resolved` **в той же транзакции**.
- **Отклонить** — `POST /admin/reports/{id}/dismiss {resolution}`: пояснение обязательно, закрываются все открытые жалобы на ту же цель.
- В обоих случаях авторы жалоб получают уведомление с пояснением. Свои жалобы и решения пользователь видит в `GET /my/reports`.

## 9. Дополнительные механики

| Механика              | Правила                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **«Соберём состав»**  | Пока подтверждённых меньше `min_participants`, у события `quorum_status=gathering`. Набрали — `reached`, участники и организатор получают «Состав собран». | **«Встречу новичка»** | При записи можно отметить «иду впервые» (`first_time`). Подтверждённый участник, который не новичок, может стать проводником (`POST /events/{id}/buddy`). Платформа автоматически назначает пару, у одного проводника не больше 3 новичков. Оба получают имена друг друга. | **«Ищу компанию»**    | `POST /my/company-requests`: направление (из списка или своё), уровень, части дня, дни недели, район словами, необязательная точка с радиусом. Один активный запрос на направление (409), срок жизни 30 дней. Подбор — одно SQL-условие: направление совпадает, событие опубликовано и не началось, автор события не автор запроса, уровень совместим, совпадают часть дня и день недели (по местному времени), расстояние проверяется только если точки есть с обеих сторон. Обезличенный спрос для организатора — `GET /sports/demand` («12 человек ищут»). |
| **Напоминания**       | Автоматически за сутки и за 2 часа до начала, плюс кнопка организатора `POST /events/{id}/remind` (не чаще раза в час, иначе 409). Подтверждённые участники получают время, адрес, точку сбора, что взять, погоду и имя проводника. Повторно одно и то же напоминание не уходит. После переноса напоминания приходят заново.                                                                                                                                                                                                                                                                                                                                                                                         |
| **Погода**            | `GET /events/{id}/weather` для уличных встреч (Open-Meteo, без ключа, с таймаутом). Ответ: `{available, reason, forecast}`. Сбой прогноза не ломает карточку и напоминание.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Другие встречи**    | `GET /events/{id}/alternatives?limit=` — похожие предстоящие встречи после отказа, отмены, снятия или «мест нет».                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

## 10. Уведомления

Любое решение кладёт в outbox событие `notification.requested` `{user_id, title, body, link, email?}` в той же транзакции. Сервис notifications сохраняет уведомление идемпотентно по id события, отдаёт его в SSE-поток, отправляет письмо и, если подключён, MAX.

**Поводы для уведомления:**

- новая запись, заявка или запись в лист ожидания — организатору;
- решение по заявке, исключение из состава, подтверждение из листа ожидания — участнику;
- допуск или отказ организации — представителю, с причиной;
- снятие, удаление, отмена события — организатору и всем записавшимся;
- новый вопрос — организатору; ответ — автору вопроса;
- скрытие и возврат сообщения — автору;
- решение по жалобе — автору жалобы;
- «Нашлась компания»;
- «Состав собран» и «Встреча не состоится»;
- назначение проводника;
- перенос события и изменение условий;
- напоминания.

**API колокольчика:**

- `GET /notifications` — `{items, unread}`;
- `GET /notifications/stream` — SSE-поток новых уведомлений;
- `POST /notifications/{id}/read`, `/read-all`;
- MAX — `/notifications/max`, `/notifications/max/link`.

## 11. Админка-аналитика (moderation) и доменные события

- **Доменные события.** Каждый переход статуса в events пишет `status_history` и ставит в outbox `domain.<сущность>.changed` со **снимком сущности после изменения**. Сущности: organization, event (включая состав), participation, comment, company_request.
- **Версия снимка.** У каждого снимка есть `version` — счётчик `domain_version`, который растёт под блокировкой строки. moderation принимает снимок, только если его версия больше сохранённой. Это исправленная ошибка: раньше сравнивалось время начала транзакции, и запоздавшая транзакция могла откатить проекцию. Старые сообщения без версии сравниваются по времени и не могут перезаписать версионированный снимок.
- **Проекции и журнал.** moderation хранит свои проекции и журнал модерации (дедупликация по id сообщения). В журнал попадают решения по организациям, переходы событий, скрытие и возврат сообщений.
- **Маршруты** (все — роль `admin` в gateway **и** в сервисе):
  - `GET /admin/moderation/dashboard` — заявки организаций (давние первыми), счётчики по статусам, ряд за 14 дней, топ направлений, `updated_at` для оценки свежести;
  - `GET /admin/moderation/log?entity=&to=&entity_id=&q=`;
  - `GET /admin/moderation/comments?status=&event_id=&q=`;
  - `GET /admin/moderation/reports/{events,organizations,log}.csv` — UTF-8 с BOM, разделитель «;», защита от формул Excel.
- **Догнать проекции:** `POST /admin/domain/republish` (в events) переотправляет снимки всех сущностей, например после очистки базы moderation.
- **Журнал действий:** `GET /admin/audit` — все изменяющие запросы всех пользователей (сервис audit).
- **Учётные записи обычной регистрации:**
  - поиск по почте и имени — `GET /admin/accounts?q=&status=`, символы `%` и `_` в запросе экранируются;
  - карточка с историей — `GET /admin/accounts/{id}`;
  - блокировка с причиной — `POST /admin/accounts/{id}/block`, разблокировка — `/unblock`.

## 12. Общие правила API

- **Права.** Владелец записи всегда берётся из `X-User-ID`, а не из тела запроса. Проверка «это моё» выполняется в SQL. Админские маршруты закрыты ролью дважды: в gateway и в сервисе.
- **Ошибки:** `{"error": {"code", "message", "field?", "request_id"}}`, сообщения по-русски и без внутренних деталей. Внутренние детали пишутся в лог с `request_id`, который проходит через gateway, сервисы, outbox и обработчики.

| Код   | Смысл                                                                                                                                      |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `400` | Сломанный JSON, лишние поля (JSON-декодер отклоняет неизвестные поля), неверные параметры запроса, не UUID                                 |
| `401` | Нет сессии или токена, неверный пароль                                                                                                     |
| `403` | Нет прав: организация не допущена, решение не организатором, чужое сообщение, нет роли admin, чужой `Origin`, учётная запись заблокирована |
| `404` | Не найдено или скрыто от вас (снятое событие для постороннего)                                                                             |
| `409` | Состояние не позволяет: снято, прошло, мест нет, уже решено, повтор, запрещённый переход (`invalid_transition`), запись после отказа       |
| `422` | Неверное поле (`validation_error` + `field`) или нет обязательной причины (`reason_required`)                                              |
| `429` | Лимит. Срок — в `Retry-After`                                                                                                              |
| `502` | Недоступен сервис за gateway (`upstream_unavailable`)                                                                                      |
| `503` | Временный сбой Redis или identity; сессия при этом сохраняется                                                                             |

- **Лимиты:**
  - 60 изменяющих запросов в минуту на пользователя (общий счётчик в Redis);
  - 10 запросов в минуту к LLM;
  - лимиты входа и жалоб — см. разделы 2.2 и 8.
- **Идемпотентность.** `Idempotency-Key` у изменяющих запросов: повтор в течение 24 часов возвращает сохранённый ответ с заголовком `Idempotent-Replayed: true`. Тот же ключ для другого метода или пути — `422 idempotency_key_reused`, пока первый запрос выполняется — `409 request_in_progress` (тело запроса в отпечаток не входит). Ошибка 5xx освобождает ключ, причём очистка выполняется с независимым контекстом и таймаутом. Это исправленная ошибка: после обрыва соединения ключ раньше зависал «в обработке» на сутки.
- **Даты** — RFC 3339 в UTC; время дня и дни недели для подбора считаются по Красноярску. **Списки** — `{items, total, limit, offset}`.

## 15. Известные ограничения (сознательные)

- **Посещение не проверяется:** «записались», а не «пришли».
- **Лимиты входа считаются по почте и общим счётчиком, а не по IP:** nginx перед gateway не передаёт адрес клиента.
- **Открытые сессии заблокированного пользователя закрываются за время до 30 секунд**, новый вход закрывается сразу.
- **Регистрация раскрывает занятость почты** (409 `email_taken`) — привычный компромисс в пользу удобства.
- **Подтверждения почты, восстановления пароля и SMS нет:** постановка их не требует.
- **Шаблон realm Keycloak применяется только при первом запуске.** Для существующего тома нужен `make keycloak-sync`.
- **Хаб SSE уведомлений живёт в памяти процесса.** При нескольких репликах нужен общий канал.
- **Админка-аналитика отстаёт на секунды:** она построена на событиях.
- **Сервис `tasks` — образец шаблона**, к домену не относится.
- **Фронтенд ещё не использует** `/auth/local/*`, жалобы, удаление и возврат сообщений, исключение участника. Ручки описаны в `frontend-api.md`.
