# Архитектура

## Путь запроса

Браузер получает Vite SPA. В Docker Nginx раздаёт `dist`, возвращает `index.html` для маршрутов React Router и проксирует `/api/` и `/auth/` в Go. При локальной разработке это делает Vite proxy. Адрес Go upstream задаётся конфигурацией прокси, клиент не может выбрать произвольный сервер.

Go проверяет авторизацию, назначает `X-Request-ID`, ограничивает тело запроса и выполняет обработчик. Redis ограничивает изменяющие запросы: 60 в минуту на пользователя. Репозитории включают `owner_id` в SQL для чтения, изменения и удаления.

## Вход и сессия

`GET /auth/login` сохраняет в Redis случайный одноразовый `state`, PKCE verifier и проверенный внутренний путь возврата на 10 минут. Случайный state также записывается в короткоживущую HttpOnly cookie. В Keycloak передаётся challenge S256.

`/auth/callback` требует совпадения state и cookie, одноразово читает запись Redis, обменивает код с PKCE и проверяет access token. Токены остаются в Redis, браузер получает только случайный идентификатор `starter_session`: HttpOnly, SameSite=Lax, Path=/, Secure при HTTPS. Срок сессии ограничен восемью часами.

Сессия действует восемь часов с момента входа; активность не продлевает этот срок. Go автоматически обновляет access token по refresh token внутри этого срока. Браузер не обновляет сессию и не повторяет запросы после 401: `/me` возвращает отсутствие пользователя, остальные защищённые запросы переводят на вход. Сбой Redis возвращает 503 без очистки cookie. Параллельные обновления одной сессии объединяются в процессе API. В локальном realm ротация refresh token выключена; для включения ротации при нескольких API нужна распределённая блокировка. Обновление использует `SET XX`, чтобы не восстановить удалённую при выходе сессию.

`POST /auth/logout` удаляет сессию Redis, очищает cookie и возвращает URL завершения SSO Keycloak. Фронтенд открывает этот URL; Keycloak может показать подтверждение. После удаления сессии браузер теряет доступ немедленно. Внешний JWT действует до `exp`.

Для изменяющих cookie-запросов Go требует точный `Origin=APP_ORIGIN`. Bearer-клиенты не используют cookie-сессию. Redis временный: после его перезапуска нужен повторный вход.

## Пользователи и права

Keycloak хранит пользователей; `sub` становится владельцем задач и файлов. `go-oidc` проверяет подпись, issuer, audience и срок действия JWT. В Docker discovery и JWKS идут по внутреннему адресу, issuer в токене остаётся публичным.

`/me` возвращает `{id,email,name,roles}`. Роли — `user` и `admin`; демопользователи получают `user`. Администратор Keycloak и admin приложения различаются. Клиентская проверка ролей управляет интерфейсом, доступ ограничивает Go.

## Файлы и данные

PostgreSQL хранит задачи и метаданные, S3 — закрытые объекты. Ключ объекта состоит из sub и UUID. Списки задач и файлов используют пагинацию и согласованный снимок count/items. Исходное имя файла не используется как путь.

При загрузке проверяются размер до 10 МиБ и фактический тип PNG, JPEG, WebP, PDF или текста. Скачивание идёт через Go с проверкой владельца, `Content-Disposition: attachment` и `nosniff`. При ошибке сохранения метаданных API пытается удалить объект. Для длительной эксплуатации нужна сверка объектов с базой; антивирус и квоты пока не реализованы.

Goose-миграции встроены в бинарник. Контейнер migrate завершается перед API. Применённые миграции не редактируются, изменения добавляются отдельными файлами.

Удаление файла сначала проверяет владельца и получает ключ из PostgreSQL, затем удаляет объект из S3 и только после успеха — метаданные. При сбое S3 запись остаётся для повтора. Если после удаления объекта недоступна БД, повтор безопасен: удаление отсутствующего объекта S3 успешно. Во время такого сбоя запись может временно оставаться в списке без доступного содержимого.

## Микросервисы бэкенда

Бэкенд состоит из независимых Go-модулей. У каждого свой `go.mod`, зависимости, конфигурация, Dockerfile и образ; общего кода между ними нет, контракт — только HTTP и два заголовка.

| Сервис          | Модуль         | Роль                                                                                                                                                              | Хранилище                   |
| --------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `api` (gateway) | `apps/gateway` | Единственный публичный вход: вход через Keycloak, сессии и JWT, `/me`, роли, CSRF, лимит 60 изменений в минуту, проксирование `/api/v1/tasks*` и `/api/v1/files*` | Redis                       |
| `tasks`         | `apps/tasks`   | Домен задач                                                                                                                                                       | база `tasks` в Postgres     |
| `files`         | `apps/files`   | Домен файлов                                                                                                                                                      | база `files` в Postgres, S3 |
| `llm`           | `apps/llm`     | Шлюз к локальной модели (Ollama, Qwen): `POST /api/v1/llm/generate`, `POST /api/v1/llm/stream` (SSE), `GET /api/v1/llm/status`                                    | Ollama                      |

Миграции встроены в бинарник каждого сервиса (`tasks migrate up`) и применяются к его собственной базе; в Compose это `tasks-migrate` и `files-migrate`. Браузер и Nginx обращаются только к gateway на порту 8080; `tasks` и `files` портов наружу не публикуют.

**Доверие между сервисами.** Gateway проверяет пользователя, затем удаляет присланные клиентом `Authorization` и `Cookie` и добавляет `X-User-ID` (это `sub`) и общий секрет `X-Internal-Token`. Внутренний сервис (`platform.TrustGateway`) сравнивает токен за постоянное время и берёт владельца записей из `X-User-ID`, поэтому запрос в обход gateway получает 401. Секрет `INTERNAL_TOKEN` создаёт `make setup`. Для production стоит добавить mTLS или сетевые политики: общий секрет защищает только от вызова без знания токена.

**Готовность.** `/readyz` gateway проверяет Redis и `/readyz` обоих сервисов; `/readyz` `tasks` проверяет Postgres, `files` — Postgres и S3. Недоступный сервис в ответ на запрос даёт 502 `upstream_unavailable`, остальные части приложения продолжают работать.

**LLM.** `llm` не хранит данные и не зависит от Ollama при старте: без профиля `llm` (`make llm`) сервис готов, `status` показывает `available:false`, а генерация отвечает 503. Защита дорогого ресурса: лимит 10 запросов в минуту на пользователя в gateway (Redis), не более `LLM_MAX_CONCURRENT` одновременных генераций в сервисе (остальные получают 429 `model_busy`), предел длины запроса `LLM_MAX_PROMPT_RUNES`, таймаут `LLM_TIMEOUT`. Режим `json:true` включает структурный вывод Ollama; ответ всё равно нужно валидировать на стороне вызывающего домена. Стрим идёт в формате SSE (`data: {"t":"…"}`, `event: done`, `event: error`); gateway и Nginx для него продлевают таймауты и отключают буферизацию. Решения по людям принимает человек, модель только помогает.

**Уведомления.** Любой сервис уведомляет пользователя, кладя в свой outbox событие `notification.requested` (`user_id`, `title`, `body`, внутренняя `link`). `notifications` потребляет очередь `notifications.requested`, отбрасывает невалидные события (без повторов) и сохраняет уведомление идемпотентно по `id` события. Так сервисы не знают друг о друге: `tasks` после первой ИИ-проверки отправляет уведомление, не вызывая `notifications` напрямую.

**Роли в сервисах.** Gateway передаёт роли из проверенного JWT в `X-User-Roles`; сервис проверяет их через `platform.RequireRole`. Админские маршруты дополнительно закрыты в gateway (`auth.RequireRole`), например `GET /api/v1/admin/tasks/export.csv` — выгрузка всех задач в CSV (UTF-8 с BOM, «;», защита от формул Excel).

**Каналы уведомлений.** Уведомление сохраняется один раз (повторная доставка события его не дублирует), сразу уходит открытым SSE-подключениям пользователя (`/api/v1/notifications/stream`, хаб в памяти процесса — при нескольких репликах нужен общий канал, например Redis Pub/Sub) и, если в событии есть `email`, письмом через SMTP (локально Mailpit). Сбой письма логируется и не повторяет событие, чтобы не плодить дубли писем.

**Идемпотентность.** Gateway принимает `Idempotency-Key` у изменяющих запросов: первый ответ (кроме 5xx и ответов больше 1 МиБ) хранится в Redis 24 часа и возвращается на повтор с заголовком `Idempotent-Replayed: true`; тот же ключ для другого маршрута — 422, повтор во время выполнения — 409.

**Общие механизмы сервиса-образца.** В `apps/tasks/internal/platform`: `Workflow` (статусы и переходы), `ParseList` (фильтры, сортировка и поиск только по белому списку колонок), `Every` (фоновые задания с advisory lock Postgres — так чистится outbox), `NewCSV` (выгрузки для Excel). Новый сервис получает их копированием `apps/tasks`.

**ИИ-проверка и метрики.** `tasks` вызывает `llm` напрямую по внутренней сети (с `X-Internal-Token` и `X-User-ID`) только из пакета `copilot`; адрес задаётся `LLM_SERVICE_URL`, без него работают одни правила. Gateway ограничивает `POST /api/v1/tasks/{id}/analyze` тем же лимитом, что и `/llm`. Gateway отдаёт Prometheus-метрики на `GET /metrics` (`http_requests_total`, `http_request_duration_seconds`, метки — шаблон маршрута); порт 8080 в Compose привязан к localhost, Nginx `/metrics` не проксирует, в production обязателен `METRICS_TOKEN` (Bearer).

**Контейнеры.** Имя контейнера = имя сервиса в Compose, по схеме `<домен>-<роль>`:

| Контейнер                                                                         | Назначение                                                                 | Порт на хосте              |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------- |
| `gateway-service`, `tasks-service`, `files-service`, `llm-service`, `web-service` | Приложение (профиль `app`)                                                 | 8080 (gateway), 3000 (web) |
| `tasks-migrate`, `files-migrate`                                                  | Миграции сервисов, завершаются до их старта                                | —                          |
| `tasks-postgres`, `files-postgres`, `keycloak-postgres`                           | Отдельный Postgres на каждого владельца данных, свои пользователь и пароль | 5433, 5434, —              |
| `files-s3`                                                                        | Объектное хранилище файлов                                                 | 8333                       |
| `gateway-redis`                                                                   | Сессии и счётчики лимитов                                                  | 6379                       |
| `rabbitmq`                                                                        | Шина событий между сервисами                                               | 5672, консоль 15672        |
| `keycloak`, `mailpit`                                                             | Вход и тестовая почта                                                      | 8180, 8025                 |
| `llm-ollama`, `llm-ollama-pull`                                                   | Модель Qwen (профиль `llm`, `make llm`)                                    | 11434                      |

**Данные.** Сервисы не имеют общих таблиц, баз и даже экземпляров Postgres: связь только через HTTP (gateway) и события (RabbitMQ). Сквозной идентификатор — `sub` пользователя; ссылочной целостности между доменами база не обеспечивает. Данные из прежней общей базы автоматически не переносятся.

**События и RabbitMQ.** Асинхронная связь строится по схеме transactional outbox: `tasks` в одной транзакции пишет задачу и событие `task.created` в таблицу `outbox`; relay раз в секунду публикует события в exchange `events` (topic) с подтверждением брокера (publisher confirms) и помечает отправленными. Потребитель очереди `tasks.moderation` (quorum-очередь, один параллельный обработчик) выполняет ИИ-проверку и сохраняет результат в `task_moderation`; доставка at-least-once, обработчик идемпотентен (upsert). После 5 неудачных доставок сообщение уходит в `tasks.moderation.dlq` через `events.dlx`. Если брокер недоступен, CRUD работает, а события копятся в outbox и уходят после восстановления; `readyz` брокер не проверяет. Список задач содержит поле `moderation` (null, пока проверка не выполнена), фронтенд обновляет список, пока оно пусто. Новый обмен событиями между сервисами добавляется так же: свой outbox у издателя, своя очередь у подписчика, привязка к `events`.

## Границы модулей бэкенда

Каждый домен (`internal/tasks`, `internal/files`) — это `routes.go` (HTTP, только парсинг/коды ответов) → `Service` (бизнес-логика, валидация) → порты-интерфейсы (`Store` — Postgres, у `files` ещё и `Blobs` — S3), которые реализуют конкретные адаптеры (`Repository`, `S3Blobs`). `Service` зависит только от интерфейсов, поэтому его легко тестировать на фейках (`*_test.go`) без поднятия БД/S3.

Домены не импортируют друг друга. Владельца записей внутренний сервис получает от gateway (`platform.Owner(c)`). Небольшая обвязка (роутер, `TrustGateway`, пагинация) намеренно продублирована в `internal/platform` каждого сервиса: независимость модулей важнее устранения нескольких десятков строк.

Новый домен добавляется как отдельный модуль `apps/<имя>` (копия `apps/tasks`), затем маршрут и `Upstreams` в gateway. Так планируется подключить LLM (Ollama с Qwen из `compose.yaml`).

## Границы модулей фронтенда

Фронтенд: `app → pages → widgets → features → entities → shared`; зависимости только вниз. `shared` получает настройки через DI и не знает предметную область. Основной набор компонентов — Base UI в `shared/ui`; дополнительный `packages/ui` на Radix независим от приложения. Контракты импортируются из `@starter/contracts`.

WebSocket-утилиты в shared — заготовка для будущего модуля; серверного протокола и подключения по умолчанию нет. Платежи, AI, поиск и очереди не включены.

`/readyz` проверяет PostgreSQL, Redis и S3. Keycloak не входит в постоянную проверку готовности: уже выданные JWT могут проверяться по закешированным ключам, но новые входы и refresh требуют доступного Keycloak.
