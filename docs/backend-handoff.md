## 2. Запуск за 10 минут

```bash
make setup          # .env с паролями и INTERNAL_TOKEN, шаблон realm Keycloak (идемпотентно)
make up             # весь стек в Docker; первый раз — несколько минут
make keycloak-sync  # привести уже существующий Keycloak к шаблону: пользователи, роли, «Столото ID»
make seed           # данные для сценариев кейса (организации, события, заявки, сообщения)
make demo           # то же, что up + seed, и печать ссылок и учётных записей
```

**Адреса:**

| Что                     | Адрес                                                                                               |
| ----------------------- | --------------------------------------------------------------------------------------------------- |
| Приложение и Swagger    | `http://localhost:3000`, `/api/docs`                                                                |
| Gateway напрямую        | `http://localhost:8080`                                                                             |
| Keycloak («Столото ID») | `http://localhost:8180`, логин админа — `KEYCLOAK_ADMIN` из `.env`                                  |
| RabbitMQ                | `http://localhost:15672`                                                                            |
| Почта (Mailpit)         | `http://localhost:8025`                                                                             |
| Базы на хосте           | tasks 5433, files 5434, notifications 5435, audit 5436, events 5437, moderation 5438, identity 5439 |

**Учётные записи.** Пароли лежат в `.env`, `make demo` их печатает. Все шесть аккаунтов — пользователи «Столото ID»: Анна и Игорь (пользователи), Олег (организация «Ладья», допущена), Мария («Сосны», на проверке), Пётр («Пульс», отклонена), Модератор (admin). Обычная регистрация — `POST /auth/local/register` или форма на фронте, когда её сделают.

**Сервис вне Docker.** Сначала `make infra`, затем `make events`, `make identity`, `make gateway` и т. д. Порты сервисов задаёт Makefile: events :8087, moderation :8088, identity :8089.

**Ловушка.** После пересоздания контейнера gateway nginx во `web-service` держит старый IP и отвечает 502. Лечится так: `docker compose --profile app up -d --force-recreate web-service`. `deploy.sh` делает это сам.

## 3. Карта бэкенда

Каждый сервис — отдельный Go-модуль со своим `go.mod`, своей базой и миграциями. Общего Go-кода нет: обвязка `internal/platform` и `internal/broker` скопирована в каждый сервис. Исправление в такой обвязке переносите во все копии.

```
server/
  gateway/      публичный вход :8080 (Redis)
    internal/auth/       session.go — SSO-сессии и общий механизм; local.go — вход по паролю; auth.go — Middleware, роли
    internal/httpapi/    server.go — роутер и прокси по префиксам; idempotency.go; proxy.go — заголовки X-User-*
    internal/config/     переменные окружения и проверки для production
  identity/     учётные записи обычной регистрации (Postgres identity)
    internal/accounts/   model.go — правила полей; password.go — Argon2id; service.go — вход/регистрация/блокировка;
                         repository.go — SQL; routes.go — /internal/v1/* и /api/v1/admin/accounts
  events/       ВЕСЬ ДОМЕН кейса (Postgres events)
  moderation/   админка-аналитика на доменных событиях (Postgres moderation)
  notifications/ realtime/ audit/ files/ llm/   вспомогательные сервисы
  tasks/        образец шаблона, к домену не относится
```

## 4. Как проходит запрос

На примере записи на событие `POST /api/v1/events/{id}/join` из браузера.

1. **nginx** (`web-service`, :3000) проксирует `/api/` и `/auth/` в gateway.
2. **gateway**, `server.go`, по порядку:
   1. `request_id` и лимит тела;
   2. CSRF: у изменяющего запроса с cookie `Origin` должен совпадать с `APP_ORIGIN`;
   3. `auth.Middleware`: сессия из Redis по cookie. SSO-сессия даёт access token, gateway при необходимости обновляет его и проверяет JWT. Local-сессия даёт сохранённого пользователя, статус которого раз в 30 секунд сверяется с identity. Результат — `Identity` в контексте;
   4. лимит 60 изменений в минуту и `Idempotency-Key` (Redis);
   5. журнал действий (публикация `audit.recorded`);
   6. `proxy()`: удаляет `Authorization` и `Cookie`, ставит `X-Internal-Token`, `X-User-ID`, `X-User-Roles`, `X-User-Email`, `X-User-Name`.
3. **events:**
   1. `platform.TrustGateway` сверяет секрет за постоянное время;
   2. `profileSync` обновляет копию имени в `profiles`;
   3. маршрут собирает `Actor` из заголовков, `withID` проверяет UUID;
   4. `Service.Join` проверяет вход, затем `Repository.Join`.
4. **Транзакция в `Repository.Join`:**
   1. `lockEvent` — `SELECT … FOR UPDATE` по событию;
   2. проверки статуса, времени, организатора и прошлого отказа;
   3. подсчёт мест, `INSERT … ON CONFLICT`;
   4. `record()`: `status_history` + `domain.participation.changed` в outbox с версией;
   5. `notify()`: `notification.requested` организатору;
   6. `afterConfirmed()`: состав и проводники — **всё в одной транзакции**.
5. **Relay outbox** публикует события в exchange `events` с подтверждением брокера. Дальше:
   - `notifications` сохраняет уведомление (идемпотентно), шлёт его в SSE и почту;
   - `moderation` применяет снимок к проекции, если версия больше сохранённой;
   - `realtime` получает `realtime.publish` для обсуждения.
6. **Ответ.** Доменная ошибка проходит через `handle()` и становится `{error: {code, message, field?, request_id}}` с нужным статусом. Для 500 детали остаются только в логе с тем же `request_id`.

## 5. Авторизация: как работают два способа входа

**«Столото ID» (Keycloak, SSO-заглушка):**

1. `GET /auth/login`: state и PKCE verifier сохраняются в Redis на 10 минут, затем редирект в Keycloak.
2. `/auth/callback`: обмен кода, проверка токена, `save()` новой сессии.
3. Сессия хранит токены. Middleware отдаёт access token и обновляет его по refresh token (`singleflight` в пределах процесса).

**Почта и пароль (identity):**

1. `POST /auth/local/register|login`. Gateway проверяет лимит по почте, затем вызывает `identity /internal/v1/*` с `X-Internal-Token`.
2. identity проверяет Argon2id и статус и возвращает учётную запись.
3. Gateway выполняет `startLocal()`: сессия `{local: Identity}`, id сессии добавляется в `user_sessions:<id>`, ставится кеш `account_active:<id>` на 30 секунд.
4. Middleware берёт пользователя из сессии. Когда кеш истёк, `checkLocal()` спрашивает identity о статусе: заблокирован — сессия удаляется и ответ 401.
5. Смена пароля закрывает все сессии из `user_sessions:<id>`, кроме текущей.

**Роли.** `admin` выдаёт только Keycloak, identity всегда отдаёт `["user"]`. Админский маршрут закрыт **дважды**: `auth.RequireRole("admin")` в gateway и `platform.RequireRole("admin")` в сервисе. Организатор и представитель организации — не роли, а данные, и проверяются в SQL.

## 6. Паттерны кода, которые нужно повторять

| Паттерн           | Как                                                                                                                                                                                                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Слои              | `routes` (разбор HTTP) → `Service` (валидация, нормализация) → `Store`/`Repository` (SQL в транзакции). У `Service` нет SQL, у `Repository` нет HTTP. В юнит-тестах сервиса — фейк `Store`                                                                                                      |
| Ошибки            | Доменная ошибка — переменная `errors.New("сообщение для человека")`. Ошибка поля — `FieldError{field, message}` (422). Новую ошибку **обязательно** добавьте в `handle()` (`routes.go`), иначе вернётся 500                                                                                     |
| Права             | Только из `actor(c)` (`X-User-ID`), никогда из тела запроса. Проверка «моё» — в SQL или под блокировкой (`e.OrganizerID != a.ID`)                                                                                                                                                               |
| Конкурентность    | Любое изменение участия, мест или статуса события начинается с `lockEvent()` (`FOR UPDATE`). Порядок блокировок: сначала событие, потом записи. Не держите транзакцию во время внешних вызовов (погода, LLM)                                                                                    |
| Статусы           | Переходы проверяет `platform.Workflow` (`orgWorkflow`, `eventWorkflow` в `model.go`), обязательные причины — `RequireComment`. Неверный переход даёт `ErrTransition` (409)                                                                                                                      |
| История и события | Каждый переход статуса — `record(ctx, tx, entityType, id, Transition{…})` в той же транзакции: пишет `status_history` и `domain.<entity>.changed` со снимком (`snapshots` в `domain.go`) и монотонной `domain_version`. Новую сущность для moderation добавляйте в `snapshots` и `domainTables` |
| Уведомления       | `notify(ctx, tx, userID, title, body, link)` — в той же транзакции, через outbox. Тексты по-русски и понятные человеку                                                                                                                                                                          |
| Realtime          | `publishChanged(ctx, tx, …)` — только сигнал «перечитай», данные клиент берёт из API (канал `room:` доступен на запись любому вошедшему)                                                                                                                                                        |
| Фоновые задачи    | `platform.Every(ctx, db, log, name, interval, job)`: advisory lock, поэтому выполняется одной репликой. Внутри задачи **перепроверяйте условия под блокировкой** (пример — `failQuorum`)                                                                                                        |
| Списки            | `platform.ParsePagination` (limit 1–100, offset до 100000), ответ `{items, total, limit, offset}`. Значения фильтров — только параметрами SQL                                                                                                                                                   |
| Миграции          | Только новым файлом `000NN_*.sql` с `-- +goose Up/Down`. Применённые не правим. Ограничения (`CHECK`, `UNIQUE`) — в базе, а не только в Go                                                                                                                                                      |
| Комментарии       | По-русски и о причинах и ограничениях, а не пересказ кода                                                                                                                                                                                                                                       |

## 7. Как добавить фичу: чек-лист

1. Найдите строку в чек-листе [case.md](case.md), которую двигает фича.
2. Напишите миграцию (новый файл), с ограничениями в базе.
3. Опишите модель и ошибки в `model.go` или новом файле домена, валидацию — в `Service`.
4. Сделайте метод `Repository` в `inTx`: блокировка → проверки → изменение → `record` → `notify` и `publishChanged`. Добавьте метод в интерфейс `Store`.
5. Добавьте маршрут в `register*`, новые ошибки — в `handle()`.
6. Если нужен новый URL-префикс, добавьте его в список gateway (`server/gateway/internal/httpapi/server.go`). Для админского — с `auth.RequireRole("admin")`.
7. Опишите маршрут в `server/<сервис>/api/openapi.yaml` со всеми кодами ошибок. Тест `api/spec_test.go` упадёт, если маршрут не описан.
8. Выполните `make openapi`: соберётся общий OpenAPI, TS-типы и копия для Swagger. Zod-схемы форм — в `packages/contracts/src/sport.ts`, с тестом.
9. Добавьте строку в [frontend-api.md](frontend-api.md) — это контракт для фронтенда — и правила в [data-model.md](data-model.md).
10. Тесты:
    - юнит — на валидацию;
    - интеграционный — на транзакцию и гонки (`*_integration_test.go` с `isolatedDB`);
    - блок в `scripts/case-smoke.mjs`, если это пользовательский сценарий.
11. Перед сдачей: `make check`, `make integration`, `make smoke`, `make case`.

## 9. Что сделано в последней итерации

- **Семь ошибок из ревью исправлены и покрыты тестами** (таблица в [backend-review.md](backend-review.md#13-исправления-по-предыдущему-ревью)):
  - снимок организации после повторной подачи;
  - автоотмена перенесённого события;
  - правка после срока сбора;
  - места при увеличении лимита — сначала очереди;
  - зависший `Idempotency-Key`;
  - NaN и Inf в гео-фильтре;
  - версии доменных снимков вместо `now()`.
- **Две авторизации.** Новый сервис `server/identity` (Argon2id, защита от подбора, блокировка админом, история). Gateway: `/auth/providers`, `/auth/local/register|login|password`, локальные сессии, `provider` в `/me`, прокси `/admin/accounts`. Keycloak оформлен как «Столото ID», самостоятельная регистрация в нём выключена.
- **Демо-вход «Войти как…» убран:** `demo.go`, `DEMO_LOGIN`, переменные gateway. Seed не запускается автоматически: только `make seed`.
- **Модерация:**
  - жалобы на события и сообщения с очередью у админа и автозакрытием при принятых мерах;
  - автор может удалить своё сообщение, админ — вернуть скрытое;
  - организатор может исключить участника, место переходит очереди.
- **Бизнес-дыра закрыта:** после отказа или исключения записаться снова нельзя (409).
- **Инфраструктура:** identity добавлен в compose (dev и prod), `deploy.sh`, бэкапы и Makefile. `make keycloak-sync` приводит существующий realm к шаблону. Проверка деплоя выровнена.
- **Проверки и тесты:**
  - smoke и case-smoke дополнены новыми проверками;
  - e2e регистрации переписан под обычную регистрацию;
  - фронтовые e2e починены: обучение и анимации отключены в тестах;
  - в клиенте исправлены три нарушения доступности (axe) и шапка на телефоне.

## 10. Что осталось и где граница

- **Сдача (пункт 13 кейса).** Нужны стенд по сети (`compose.prod.yaml` + Caddy, `deploy/`), репозиторий в GitVerse, README с учётными записями. Делается отдельным решением команды.
- **Фронтенд** ещё не использует `/auth/local/*`, жалобы, удаление и возврат сообщений, исключение участника. Всё описано в [frontend-api.md](frontend-api.md), Zod-схемы и типы есть в `@starter/contracts`.
- **Образец `tasks`** по плану кейса удаляется из навигации и проекта, когда фронт перейдёт на домен.
- **Сознательные ограничения:**
  - лимиты входа считаются по почте, а не по IP (nginx не передаёт адрес клиента);
  - блокировка закрывает открытые сессии за время до 30 секунд;
  - хаб SSE живёт в памяти процесса;
  - посещение не проверяется.

  Полный список — в [backend-review.md](backend-review.md#15-известные-ограничения-сознательные).

## 11. Частые вопросы

- **Почему весь домен в одном сервисе?** Допуск организации, статус события и запись проверяются в одной транзакции под одной блокировкой. Разнести их — значит получить распределённую согласованность без пользы, а жюри прямо пишет, что число сервисов баллов не даёт.
- **Почему moderation — отдельный сервис?** Тяжёлые выборки и CSV админа не нагружают базу, в которую идёт запись. Граница проходит по независимым данным (проекциям из событий), а не по таблицам.
- **Почему identity отдельно от Keycloak?** Это продуктовое решение: «Столото ID» — внешний единый вход компании (у нас тестовый стенд), а обычная регистрация — наша. Так роль `admin` невозможно получить регистрацией, а домену всё равно, как вошёл пользователь.
- **Как догнать админку-аналитику после очистки её базы?** `POST /api/v1/admin/domain/republish` (это же вызывает `make seed`).
- **Изменил шаблон realm — почему Keycloak не видит изменений?** Он импортирует realm только в пустую базу. Выполните `make keycloak-sync`.
